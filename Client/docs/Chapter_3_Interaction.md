# Chapter_3 - Interaction 학습 로그

## 문서 목적

이 문서는 locomotion 기반이 어느 정도 정리된 뒤,
`Interact` 기능을 상태머신 위에 얹는 과정에서 나온 질문과 판단을 정리한 학습 로그다.

핵심은 단순히 스위치를 누르게 만든 것이 아니라:

- 상호작용을 어떤 구조로 넣을지
- 입력, 탐지, 실제 실행을 어떻게 분리할지
- 이후 NPC 대화, 퀘스트, 무기 줍기까지 어떻게 확장할지

를 기준 중심으로 정리하는 것이다.

---

## 이번 챕터의 핵심 주제

이번 챕터의 핵심은 아래 한 줄로 정리된다.

**상호작용은 버튼 입력 하나로 바로 실행하는 기능이 아니라, “탐지 + 상태 전환 + 실제 실행”의 흐름으로 다뤄야 한다.**

즉 상호작용도 그냥 `if (E pressed) Interact();`로 끝내지 않고,
locomotion 구조 위에 하나의 행동 흐름으로 얹는 기준을 세우는 작업이었다.

---

## 시작 시점의 문제

초기에는 다음 요소들이 따로 존재했다.

- `Interact` 입력
- `InteractionDetector`
- `IInteractable`
- `SwitchInteractable`, `NPCInteractable`, `WeaponPickUpInteraction`

하지만 이 셋은 연결되어 있지 않았다.

즉:

- 입력은 들어오지만
- 무엇과 상호작용 가능한지 state가 모르고
- 실제 `Interact(...)` 호출도 state 흐름에 연결되지 않았다.

겉보기에는 시스템이 있어 보여도,
실제로는 “동작하지 않는 조각들”에 가까웠다.

---

## 이번 챕터에서 던졌던 질문

### 1. Interact는 즉시 실행형으로 갈까, 상태로 갈까?

여기서 두 가지 선택지가 있었다.

#### 선택지 A. 즉시 실행형

- `GroundState`에서 `ConsumeInteractPressed()` 확인
- 대상 있으면 바로 `Interact(gameObject)` 호출

장점:

- 빠르고 단순함

단점:

- 애니메이션 타이밍을 넣기 어려움
- 이후 대화, 문열기, 퀘스트 시작 같은 연출형 상호작용으로 확장하기 어려움

#### 선택지 B. `InteractState`

- 입력 확인
- 대상 확인
- `InteractState` 진입
- 애니메이션 시작
- 짧은 delay 후 실제 `Interact(...)`
- 다시 `GroundState` 복귀

이번 챕터의 결론은 명확했다.

**지금은 최소 구현이라도 `InteractState`로 가는 게 맞다.**

이유는 이후:

- NPC 대화
- 퀘스트 수락
- 무기 줍기
- 문/레버/상점

같은 기능을 다 같은 패턴으로 확장할 수 있기 때문이다.

---

### 2. 탐지는 어디서 해야 하나?

처음에는 state 안에서 직접 탐지할 수도 있어 보였다.

하지만 그렇게 하면:

- 물리 탐지 책임
- 상태 판단 책임
- 실제 실행 책임

이 다시 한 군데로 모인다.

그래서 결정한 기준은:

- `InteractionDetector`: 탐지
- `GroundToInteractTransition`: 입력 + 대상 유무 판단
- `InteractState`: 실제 실행

즉 상호작용도 역할을 세 층으로 나눠야 한다는 점이 중요했다.

---

### 3. 상호작용 가능한 대상은 어떻게 일반화하나?

여기서 `IInteractable`의 의미가 정리되었다.

상호작용 가능한 대상은:

- 스위치
- NPC
- 무기 픽업

처럼 모두 다르다.

하지만 플레이어 쪽에서는 그 차이를 알 필요가 없다.

그래서:

```csharp
public interface IInteractable
{
    void Interact(GameObject interactor);
}
```

이 구조를 유지하는 것이 맞다고 정리했다.

즉:

**플레이어는 “무엇을 상호작용하느냐”를 몰라도 되고, 대상만 자기 로직을 수행하면 된다.**

---

### 4. Highlight도 Detector 책임인가?

탐지기를 만들면서 highlight까지 같이 다루기 시작했다.

이건 작은 설계 선택이지만 중요했다.

현재 판단은:

- 지금 단계에서는 detector가 현재 대상과 highlight까지 같이 관리해도 괜찮다
- 단, `Enable`뿐 아니라 `Disable`도 반드시 책임져야 한다

실제로 이 부분을 놓치면서:

- 시야 밖으로 나간 오브젝트 highlight가 남는 문제

가 드러났다.

즉 이번 챕터에서 다시 확인한 기준은:

**상태를 바꾸는 쪽이 아니라, “현재 탐지 대상”을 관리하는 쪽이 highlight 생명주기도 같이 책임진다.**

---

## 이번 챕터에서 틀렸던 가정

### 1. “탐지기만 만들면 상호작용이 거의 끝난다”

틀렸다.

탐지는 대상 발견일 뿐이고,
실제 상호작용 흐름은:

- 입력
- 상태 전환
- 실행
- 복귀

까지 있어야 완성된다.

---

### 2. “결과 배열의 첫 번째 콜라이더만 보면 된다”

틀렸다.

`OverlapSphereNonAlloc` 결과는 순서가 안정적이지 않다.
그래서 `_results[0]`만 보면:

- `Switch`
- `null`
- `Switch`

처럼 프레임마다 흔들릴 수 있다.

이걸 통해 배운 점은:

**탐지 결과는 “첫 번째”가 아니라 “유효한 첫 번째 대상”을 직접 찾아야 한다.**

---

### 3. “Interact를 넣어도 locomotion과 크게 충돌하지 않을 것이다”

부분적으로 틀렸다.

실제로 상호작용 상태를 넣으면 바로 다음 문제가 생긴다.

- 언제 움직임을 멈출 것인가
- 언제 다시 움직이게 할 것인가
- 애니메이션 트리거는 언제 쓸 것인가

즉 interaction도 locomotion 위에 얹히는 순간
행동 흐름 설계가 필요해진다.

---

## 이번 챕터에서 정리된 역할

### 1. `InteractionDetector`

역할:

- 전방 상호작용 대상 탐지
- 현재 유효 대상 보관
- 필요 시 highlight on/off 관리

탐지기는 실행하지 않는다.
대상을 “찾고 유지”하는 데까지만 책임을 가진다.

---

### 2. `IInteractable`

역할:

- 상호작용 대상의 공통 계약

이 덕분에 플레이어 쪽은:

- 스위치인지
- NPC인지
- 무기인지

모른 채 `Interact(...)`만 호출할 수 있다.

---

### 3. `GroundToInteractTransition`

역할:

- `Interact` 입력 소비
- 현재 유효 대상이 있는지 확인
- `InteractState` 진입 여부 결정

즉 transition은 “버튼을 눌렀다”만 보지 않고
“지금 상호작용 가능한 상황인가”까지 같이 판단한다.

---

### 4. `InteractState`

역할:

- 이동 정지 상태 진입
- 상호작용 애니메이션 시작
- 지정된 delay 후 실제 `Interact(...)` 호출

이 state는 interaction의 실행 타이밍을 담당한다.

즉:

- detector는 찾고
- transition은 들어가고
- state는 실행한다

라는 책임 분리가 만들어졌다.

---

### 5. `InteractToGroundTransition`

역할:

- 상호작용이 끝난 뒤 다시 `GroundState`로 복귀시키는 지연 전이

현재는 단순 delay 기반이지만,
이후에는 animation event나 대화 종료 이벤트 기반으로 바뀔 수 있다.

즉 지금은 최소 구조를 잡은 상태다.

---

## Switch 기반으로 무엇이 완료되었나

이번 챕터 끝 시점에서 `Switch` 기준으로는 아래 흐름이 들어갔다.

1. 플레이어가 `Interact` 버튼 입력
2. 입력 버퍼에 `InteractPressed` 기록
3. detector가 현재 상호작용 대상을 유지
4. `GroundToInteractTransition`이 조건 확인
5. `InteractState` 진입
6. delay 후 `SwitchInteractable.Interact(...)` 호출
7. 애니메이션 재생 후 `GroundState` 복귀

즉 최소 상호작용 루프는 완성되었다.

---

## NPC / Quest / Weapon으로 확장할 때의 기준

이번 챕터에서 가장 중요한 확장 기준은 이것이다.

**플레이어 쪽 상호작용 흐름은 그대로 두고, 대상 구현만 바꾼다.**

예:

- `SwitchInteractable`
- `NPCInteractable`
- `WeaponPickUpInteraction`
- 이후 `QuestInteractable`
- 이후 `ShopInteractable`

즉 상호작용 대상이 늘어나도,
플레이어 state 구조는 그대로 재사용한다.

이게 이 챕터에서 얻은 가장 중요한 설계 이점이다.

---

## 다음 단계로 이어지는 연결점

이제 상호작용 루프가 생겼기 때문에,
다음에 고민해야 하는 건 “상호작용의 내용”이다.

즉:

- NPC는 대화만 할 것인가
- 퀘스트는 어떤 데이터로 시작할 것인가
- 무기 줍기는 이후 weapon state와 어떻게 연결할 것인가

이런 문제는 interaction 흐름 위에 contents를 얹는 단계다.

따라서 다음 단계부터는:

- 대화
- 퀘스트
- 무기/상점

같은 기능을 `IInteractable` 구현체와 후속 시스템으로 분리해 붙이면 된다.

---

## 이후 같은 형식으로 로그를 쓸 때의 기준

상호작용/전투/무기 같은 챕터도 아래 기준을 유지한다.

1. 이번 챕터의 핵심 주제가 무엇인지 먼저 적는다.
2. 기능 추가가 아니라 어떤 책임을 분리했는지 중심으로 적는다.
3. 처음에 틀렸던 가정을 반드시 기록한다.
4. 최종적으로 어떤 역할이 생겼는지 명확히 나눈다.
5. 다음 챕터로 어떤 개념이 이어지는지 남긴다.

즉 로그는 구현 성공 기록이 아니라,
**설계 판단의 근거를 남기는 문서**로 작성한다.
