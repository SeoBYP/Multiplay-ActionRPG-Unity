# 26. 측정이 이끈 전투 정리 — 고칠 것과 고치지 않을 것

> **한 줄** — "동기화가 느린 것 같다"는 **체감**에서 시작했는데, 첫 커밋은 수정이 아니라 **계측**이었다. 그 데이터가 고치려던 것(틱레이트)을 **"불필요"로 기각**하고, 체감으로는 보이지 않던 **진짜 결함 2건**을 짚어냈다.
>
> **범위** 관측 인프라 · 상태 순서 역전 · 송신 직렬화 · 몬스터 레벨 스케일링 · 데이터 파이프라인
> **핵심** 측정은 "무엇을 고칠지"만이 아니라 **"무엇을 고치지 않을지"** 도 결정해 준다

---

## 1. "느린 것 같다"에는 고칠 정보가 없다

이 문장에는 **어디서**(서버 판정? 브로드캐스트? 클라 적용?), **얼마나**(10ms? 500ms?), **항상인지 가끔인지**가 전부 빠져 있다. 그래서 수정 전에 관측 경로부터 깔았다.

```
[서버]   CombatHandler / Room 틱
            → CombatTrace 구조적 로그 (Serilog Debug 스위치 — 평시 비용 0)
               경로(P→M / M→P / P→P) · 산식 문자열 · 실제 입력 · 패킷 Seq
[클라]   소켓 수신 스레드
            → CombatTraceRecorder 링버퍼 4096 (struct · 무할당 · Stopwatch 시계)
               몬스터별 집계는 링과 분리 (링이 회전해도 집계를 잃지 않는다)
[에디터] CombatTraceWindow (타임라인 / 판정 / 동기화 탭) → CSV 내보내기
```

설계에서 신경 쓴 것 두 가지:

- **평시 비용 0** — 서버는 Serilog 레벨 스위치, 클라는 구조체 링버퍼(무할당). 계측이 켜져 있다는 이유로 성능이 바뀌면 측정 자체가 오염된다.
- **링과 집계의 분리** — 링버퍼는 오래된 항목을 덮어쓴다. 집계를 링 안에서 하면 긴 세션에서 **초반 데이터가 조용히 사라진다.**

## 2. 측정이 내린 첫 판정 — "고치지 마라"

| 측정 항목 | 값 | 해석 |
|---|---|---|
| 공격 → HP 반영 지연 | **~37ms** | **RTT 지배** — 서버 처리는 병목이 아니다 |
| stale 상태 드롭 | 0건 | 송신 FIFO 이후 역전 소멸 |
| 게이트 오거부 | 0건 | 쿨다운·cadence·마나 게이트 정상 |
| 데미지 산식 | 전 건 일치 | 로그에서 AP를 역산해 대조 |

검토하던 **틱레이트 상향은 기각**됐다. 37ms의 대부분이 왕복 지연이면 **틱을 올려도 체감은 안 변하고 서버 비용만 는다.**

> **"고치지 않기로 한 결정"에 데이터 근거가 남았다는 것 자체가 수확이다.** 체감 기반으로 수정했다면 멀쩡한 것(틱레이트)을 건드리고, 진짜 결함(아래 3·4절)은 그대로 남았을 것이다.
>
> 그리고 이 판정은 [13](./chapter-13-monster-server-authority.md)에서 정한 10Hz를 **사후 검증**한 셈이다.

## 3. D2 — 시퀀스 번호는 "언제 찍는가"가 본질이다

**증상**: 몬스터 HP가 줄었다가 **되돌아간다.**

**원인**: 상태 브로드캐스트의 순서 역전. **오래된 스냅샷이 나중에 도착해 최신 값을 덮는다.**

해법으로 `S_MonsterState.Seq`를 추가했는데, 배운 것은 필드 추가가 아니라 **스탬프 시점**이었다.

```
send 시점에 스탬프      →  "나중에 보낸 것 = 큰 번호"
                            → 역전된 송신 순서를 그대로 정당화한다   ❌

snapshot 시점에 스탬프  →  "나중에 만든 상태 = 큰 번호"
                            → 클라가 seq <= applied 를 버리면 끝     ✅
```

**시퀀스 번호의 의미는 "전송 순서"가 아니라 "상태 생성 순서"다.** 송신 시점에 찍으면 번호가 도착 순서와 일치해 버려서, 정작 걸러야 할 역전을 "정상"으로 만든다.

몬스터별 `Interlocked.Increment`로 스냅샷 생성 순간에 찍고, 클라는 적용된 번호 이하를 버린다.

이 판단이 **패킷 정의에 경고로 박제**돼 있다 — `MonsterPackets.cs:45` *"⚠️ 반드시 스냅샷(생성) 시점에 `NextSeq()`로 찍는다. 송신 시점에 찍으면…"*. 다음 사람이 같은 함정에 빠질 자리에 답이 미리 놓여 있다.

## 4. D1 — "재현 안 됨"은 "버그 없음"이 아니다

여러 스레드(틱·핸들러)가 한 소켓에 동시에 `Send`하면 **프레임이 절반씩 섞여** 역직렬화가 깨질 수 있다. 수정은 세션당 **송신 큐 단일화**다.

```csharp
// Session.cs:46 — SingleReader = "프레임 원자성의 근거"
_sendQueue = Channel.CreateBounded<byte[]>(1024, new() { SingleReader = true, FullMode = Wait });
// :192  틱 스레드가 생산자 → 절대 블록시키지 않는다 → TryWrite 만 사용
//       실패 = 큐 포화 = 사실상 죽은 연결 → 그 세션 Disconnect
```

세 가지 결정이 붙어 있다.

- **소비자 하나**(`SingleReader`)가 전체 프레임 단위로 쓴다 → 섞일 수 없다.
- **생산자는 절대 대기하지 않는다**(`TryWrite`) → 느린 클라 하나가 틱 스레드를 멈추지 못한다.
- **포화되면 끊는다** → 무한 큐는 느린 클라가 서버 메모리를 먹는 **DoS 벡터**다.

### 검증에서 배운 것

"수정을 껐다 켜서 테스트가 실패를 잡는지 확인한다"는 규율대로 우회 실험을 했는데 — **두 번 다 통과해 버렸다.**

```
1차 실패 이유: 페이로드가 커널 버퍼보다 작아 한 번에 나갔다
2차 실패 이유: Windows 의 overlapped WSASend 는 전체 버퍼 완료까지 원자적이다
⇒ 이 버그는 Windows 에서 구조적으로 재현되지 않는다. Linux(운영 환경)에서는 실재한다.
```

> **"재현 안 됨"은 "버그 없음"이 아니라 "이 플랫폼에서는 안 보임"일 수 있다.** 그래서 이 수정의 근거는 재현이 아니라 **구조 보장**이다 — 송신 경로가 큐 하나로 수렴하므로 **어떤 플랫폼에서도** 프레임이 섞일 수 없다. 테스트는 재현 대신 **순서·포화·끊김 정책**을 지킨다.

**부수 효과 하나가 계약 변경이었다** — `SendPacketAsync`의 의미가 "전송 완료"에서 **"큐 적재 완료"**로 바뀌었다. 시그니처가 같아도 **의미가 바뀌면 계약 변경**이라 주석으로 박제했다.

## 5. 관측 도구도 설계 대상이다

클라 레코더의 첫 판은 **내 스윙만** 기록했다(공격 송신 시점에 레코드를 시작하므로). 지적이 바로 왔다 — 검수 목적은 "내 데미지 확인"이 아니라 **던전 전체의 데미지·동기화 검수**인데, 다른 플레이어와 몬스터가 안 보이면 반쪽이다.

고치면서 **설계 사실 두 개**가 드러났다.

**① 몬스터가 주는 데미지에는 `S_ApplyEffect`가 없다.** 클라 입장에서 몬스터 피해의 유일한 신호는 **HP delta**다. 그래서 레코더는 HP 변화 자체를 데미지 신호로 삼는다(이동 틱의 delta 0은 제외).

**② 스윙의 출발점이 셋이라 조인 로직이 다르다** — `SwingOrigin{LocalPlayer, RemotePlayer, Monster}`. **송신→HP 지연은 로컬만** 잴 수 있고, **발동→HP 지연은 셋 다** 잴 수 있다.

### 단위 테스트가 이걸 못 잡은 이유

> **순수 로직 테스트는 내가 만든 입력으로 내가 만든 조인을 검증할 뿐, 실제 패킷 흐름에 그 입력이 존재하는지는 묻지 않는다.**

실배선 후에야 "주 시나리오(몬스터 데미지)에서 레코드 0건"이 드러났다. 계측 코드도 기능 코드다 — **요구사항(누구의 무엇을 검수하는가)을 먼저 묻고, 실재하는 데이터 소스에 배선해 검증**해야 한다.

## 6. 밸런스가 무너진 진짜 원인 — 몬스터에 레벨이 없었다

측정 CSV가 보여준 것: L6 플레이어(DEF 15) 앞에서 **몬스터 피해가 전부 1**(산식 바닥값).

몬스터는 저작 당시 스탯 그대로인데 플레이어만 성장한다. **밸런스는 시간이 지날수록 무너질 수밖에 없는 구조**였다.

진단이 정확해야 수정이 최소가 된다 — `MonsterLevelScaling.cs:22`가 그 판단을 적어 둔다: *"`StatCombatMath`는 건드리지 않는다 — **산식은 옳았고 틀린 건 base였다.**"*

### 상수를 하나도 넣지 않았다

```
base(L)  = net₁ · HP(L)/HP(1) + DEF(L)     몬스터 피해는 플레이어 HP 성장 비율을 따라간다
maxHp(L) = maxHp₁ · AP(L)/AP(1)            몬스터 체력은 플레이어 공격력 성장 비율을 따라간다
```

기각한 두 대안이 **구체적 수치와 함께** 코드에 남아 있다(`:38-39`).

| 대안 | 문제 |
|---|---|
| 곱셈 `base × (1+k(L−1))` | base가 큰 어빌리티에서 폭발 — slam(90)이 **L20에 688**, 플레이어 HP 480 → 즉사 |
| 단순 가산 `base + 4(L−1)` | 약한 몬스터는 세지고 강한 몬스터는 약해져 **전부 중간으로 수렴**(역할 붕괴) |

**플레이어 성장 곡선을 직접 읽으면** "L짜리 몬스터는 L짜리 플레이어에게 L1 때와 같은 체감"이 **정의상** 성립한다. 그리고 밸런스 조정 지점이 **레벨 테이블 한 곳**으로 수렴한다 — 조정 지점이 둘이면 반드시 어긋난다.

**L1 = 항등**이라 레벨을 저작하지 않은 기존 데이터는 스탯이 1도 변하지 않는다 — **동작 보존 증분**이고, 그 사실을 테스트가 고정한다.

## 7. 변종 = 배율이 아니라 ID

엘리트·보스를 위해 처음 만든 것은 **등급별 배율 테이블**이었다. 기각됐다 — *"Monster Table에 등급을 추가하고 ID로 구분하는 형태로. 그럼 ID만 처리하면 되잖아."*

```
배율 방식 (기각)                          ID 방식 (채택)
spawn: { id: leviathan, tier: Boss }     spawn: { id: leviathan_boss }
  → 런타임에 500 × 6.0 = 3000              → monsters.json 에 3000 을 직접 저작
  "왜 3000인지" 알려면 두 곳을 본다          한 행에 그 몬스터의 전부가 있다
```

- `tier`는 **분류 필드로만** 남는다(보스 체력바·등장 연출). **절대 스탯에 곱하지 않으며**, 그 사실을 테스트가 강제한다.
- 변종은 자기 드롭 테이블도 직접 갖는다 — 배율이 없으므로 테이블이 없으면 아무것도 떨구지 않는다(이것도 테스트).

### 이 전환 중 테스트가 내 저작 실수를 잡았다

leviathan의 base를 65로 착각하고 배율 환산해 보스를 390으로 적었는데, 원본이 500이라 **"보스가 원본보다 물렁한"** 모순이 생겼다. `변종은_별개_ID_로_저작된다` 테스트가 즉시 실패했다.

> **간접층(배율)은 코드를 줄여 보이지만 데이터를 읽는 비용을 늘린다.** 기획 데이터는 "한 행을 보면 그 몬스터의 전부를 아는" 직접 저작이 낫고, 스폰·드롭·전투가 전부 `monsterId` 하나만 다루게 되어 **코드도 오히려 줄었다.**

## 8. 데이터 전체가 한 파이프라인으로 수렴했다

```
Unity ScriptableObject 저작
   어빌리티 15 · 몬스터 13종 · 드롭 12 · 레벨 60 · 스폰 8맵
      → Exporter bake → 서버 임베디드 JSON
      → 서버·클라가 같은 카탈로그를 읽는다
      ⇒ 스킬·몬스터·던전 추가에 서버 코드 수정 0
```

지키면서 배운 것 셋:

- **Export만 있고 Import가 없으면** 재생성이 저작값을 지운다 — 모든 필드는 **왕복이 완성 조건**이다([20](./chapter-20-content-pipeline-addressables.md) 4절에서 실제로 당했다).
- **Exporter 끝의 모달 팝업이 자동화를 무기한 블록했다.** Unity가 죽은 게 아니라 팝업이 입력을 기다린 것이었다. 자동화 경로는 팝업 없는 `BakeAll()`로 분리했다 — **사람용 경로와 자동화용 경로는 다르다.**
- **구운 JSON은 생성물이다.** 직접 수정하면 다음 bake가 조용히 되돌린다. 항상 SO를 고치고 다시 굽는다.
