# 23. 전투 자원 — 보내지 않아도 맞는 값, 그리고 안 만드는 것이 정답인 작업

> **한 줄** — 마나는 HP와 같은 골격(서버 권위 + 클라 예측)을 쓰지만 **목적이 다르다.** HP 권위는 *사망 판정*을 지키고, 마나 권위는 *발동 허가*를 지킨다. 그리고 마나 값은 **매 틱 보내지 않는다** — 양쪽이 같은 식을 쓰면 안 보내도 수렴하기 때문이다.
>
> **범위** 자원 권위의 목적 · 원자적 발동 게이트 · 예측 수렴 · 베이스라인 정렬
> **부수 성과** 두 요청을 **코드 0줄**과 **최소 변경**으로 끝낸 판단 (6·7절)

---

## 1. 같은 골격, 다른 목적

[21](./chapter-21-connection-liveness-hp-authority.md)에서 HP를 서버 권위로 올렸다. 마나도 같은 형태지만 **지키려는 것이 다르다.**

| | 막는 것 | 권위가 필요한 지점 |
|---|---|---|
| **HP** | 불사 핵 (죽었는데 안 죽었다고 우기기) | **사망 판정** — 서버가 HP 0을 직접 감지 |
| **마나** | 무한 시전 핵 (자원 없이 계속 쓰기) | **발동 허가** — 서버가 "쓸 수 있는가"를 판정 |

이 구분이 설계를 갈랐다. **마나의 권위 지점은 "차감"이 아니라 "발동 허가"다.** 차감만 서버가 해도 클라가 먼저 발동해 버리면 이미 늦다.

```
입력(좌/우클릭·Ctrl)
  │
  ▼ 클라: ASC.Mana >= cost ?  ──No──▶ 발동 안 함 (송신도 안 함)   ← 즉각 거부 = 손맛
  │Yes
  ├ 예측 차감 + 애니메이션 + C_Attack / C_Dodge 송신
  ▼
서버: Mana < cost ? ──Yes──▶ 발동 거부(효과 0) ──┐
  │No                                            ├─▶ S_PlayerMana 로 owner 정정
  ├ 쿨다운 게이트 통과 → 차감 ───────────────────┘        ▼
  ▼                                        클라 EffectReceiver: ASC.Mana 덮어씀
효과 적용 (기존 경로)
```

**클라는 손맛을 위해 미리 깎고, 서버가 진실을 정정한다.** 양쪽이 같은 상수(`SkillTimeline.ManaCost`·`DodgeConfig.ManaCost`)를 보므로 정상 플레이에서는 정정이 무해하다(idempotent). 위조했을 때만 되돌려진다.

## 2. 원자 게이트 — "절반만 발동"을 없앤다

회피에는 세 가지가 함께 일어난다 — **쿨다운 소모 · 마나 차감 · 무적 부여**. 이걸 따로 검사하면 중간 상태가 생긴다.

```
❌ 쿨다운 통과 → 무적 부여 → 마나 확인 → 부족! → 거부
      이미 쿨다운과 무적을 써버렸다 (절반 발동)
```

그래서 검증·차감·효과 부여를 **한 메서드에 묶었다.**

```csharp
// PlayerState.cs:133 — 쿨다운도 마나도 통과해야 비로소 무엇도 소모된다
public bool TryBeginDodge(long nowMs, int manaCost = 0)
```

`false`를 반환하면 **아무것도 바뀌지 않는다.** 쿨다운도 그대로, 마나도 그대로, 무적도 없다.

> 같은 형태를 계속 쓰고 있다 — Main 킬 클레임의 `SET NX PX`([16](./chapter-16-main-loot-path.md) 4절), 방 결과의 `Interlocked.CompareExchange`([14](./chapter-14-dungeon-clear-loop.md) 1절). **"검사하고 나서 행동한다"를 "검사와 행동이 하나"로 바꾸는 것**이 동시성·부분실패 문제의 공통 해법이다.
>
> 회피 쿨다운 게이트 자체는 별도 치팅 방어이기도 하다 — `C_Dodge` 연사로 영구 무적을 만드는 것을 막는다(`DodgeIframeTests`가 고정).

## 3. 리젠은 왜 보내지 않는가

처음엔 "서버 권위니까 마나도 매 틱 보내야 하나?"라고 생각했다. 그런데 마나에는 **성질이 다른 두 변화**가 있다.

```
이산적 변화 (차감 · 거부)     드물다 · 정확해야 한다 · 시점이 중요하다
연속적 변화 (리젠)            잦다   · 시간에 대해 결정론적이다
```

리젠을 매 틱(100ms) 보내면 **owner 한 명에게 초당 10패킷**이 흐른다. 그런데 리젠은 `Mana += RegenPerSecond × dt`라는 **순수 함수**다 — 양쪽이 같은 rate를 쓰면 **보내지 않아도 같은 값으로 수렴한다**(둘 다 max에서 clamp).

```
클라: PlayerCharacterAgent.Update → 매 프레임 Mana += rate·dt        (예측)
서버: RoomTickService.cs:55 → Room.RegenAllPlayerMana(dt)            (권위, 패킷 0)
        └ 양쪽 모두 ManaConfig.RegenPerSecond = 10   ← Shared 단일 소스
```

**동기화 패킷은 변곡점에만 — 차감·거부·입장.**

이걸 가능하게 하는 전제가 하나 있다: **수치가 진짜 단일 소스여야 한다.** 한쪽만 바뀌면 수렴이 조용히 깨진다. 그래서 상수를 `Shared.Gameplay/Combat/ManaConfig.cs`에 두고 클라·서버가 같은 DLL을 참조한다.

설계 의도가 **패킷 정의 자체에 박제**돼 있다 — `ManaPacket.cs:7`이 "리젠은 매 틱 보내지 않는다"와 그 근거를 적어 둔다. 나중에 누가 "왜 마나가 안 오지?"라고 물을 자리에 답이 미리 놓여 있다.

> **트레이드오프** — 정확도(매 틱 스트림)를 버리고 대역폭과 단순성을 샀다. 비용은 "차감 직후~리젠 사이의 미세한 드리프트"인데, 만마에서 수렴하고 **판정이 일어나는 지점(발동 가부)에서는 항상 서버가 맞다.** 어긋남이 결과를 바꾸지 않는 자리에만 허용한 것이다.

## 4. 베이스라인 일치 — 또 만난 마지막 1마일

마나에도 [21](./chapter-21-connection-liveness-hp-authority.md)의 HP와 **똑같은 함정**이 있었다.

```
클라 프리팹 ASC     Mana(100, 100)          ← 기본값
서버 권위 MaxMana   레벨 테이블 (Lv1 = 50)   ← PlayerStats → PlayerInfo → Room

출발점이 다르면 클라는 "100 중 80", 서버는 "50 중 30" → 발동 가부가 어긋난다
```

해결도 같은 결이었다 — **입장 시 `S_PlayerMana`를 owner에게 한 번 보내** 클라 ASC의 Max/Current를 권위값으로 정렬한다(`RoomJoinLeaveHandler`). 이후에는 차감·거부 때만 보낸다.

> **"데이터가 흘러온 것"과 "판정 지점에 적용된 것"은 다르다.** `MaxMana`는 이미 GameServer가 계산하고 있었고, 빠진 건 그걸 클라 ASC에 꽂는 한 걸음이었다. 21장과 완전히 같은 형태의 누락이 다른 속성에서 반복됐다.

## 5. "공격을 Ability로 만들어줘" — 엔진을 *안* 만든 이유

요청은 *"슬라임 공격도 다 Ability로 만들고, 내가 어떤 GameplayAbility로 공격하는지 로그를 찍어줘"* 였다. 처음엔 정식 GAS 엔진(`Activate`/`Commit`/`End`, `ASC.GrantAbility`)을 떠올렸다.

그런데 두 가지를 확인했다.

- **설계 문서가 정식 어빌리티화를 의도적으로 보류**하고 있었다(`gas-architecture.md`, "확장점만 남기고 지금은 안 만든다").
- 요청자가 실제로 원한 **관찰 가능한 결과**는 "어떤 어빌리티로 공격하는지 보이는 것"이었다.

두 범위를 제시하고 골랐다.

| 범위 | 내용 | 선택 |
|---|---|---|
| **경량** | AbilityId 식별 + 발동 로그 (새 클래스·패킷 0, 로직 무변경) | ✅ |
| 정식 | Activate/Commit 엔진 + ASC 부여 + 전 공격 이관 (클라·서버 광범위) | — |

경량을 골랐고, 알고 보니 **플레이어 공격은 이미 어빌리티였다** — `SkillTimeline.Id`(`basic_swing`/`heavy_swing`)가 곧 AbilityId다. 새 데이터 없이 발동 로그만 붙이고, 슬라임에는 규약(`{monsterId}_attack`)으로 id를 부여해 로그를 통일했다.

```
플레이어  [GameplayAbility] 발동: 'heavy_swing' (mana 20, cd 1200ms)
슬라임    [GameplayAbility] slime 발동: 'slime_attack' → dmg 9 +CC slow_3s
```

> **"X로 만들어줘"를 최대 구조로 해석하지 않았다.** 문서가 보류해 둔 큰 변경을, 플레이 테스트도 못 하는 시점에, 관찰 요구 하나 때문에 들이는 건 YAGNI 위반이다. **이름 있는 식별 + 로그**로 요구를 정확히 채우고 엔진 승격은 확장점으로 남겼다.
>
> 이 판단은 나중에 검증됐다 — 발동 게이트(쿨다운·콤보 cadence·마나)는 이후 AC 트랙에서 **데이터 주도로** 들어갔고, 그때도 엔진 신설은 필요 없었다([26](./chapter-26-measured-combat-cleanup.md)).

## 6. "HUD 마나바 만들어줘" → 코드 0줄이 정답이었다

마나 로직을 깔고 나서 "HUD 마나바를 붙이자"를 다음 작업으로 잡았다. 코드를 열어 보니 **배선이 이미 전부 있었다.**

```
ASC.Mana 변화 → InGameModel.OnAttributeChanged(Mana) → InGameResult.MpChanged
   → InGameReducer.WithMp → InGameState.Mp/MaxMp → GameHud.mpSlider.SetValue
```

HP·MP·버프가 **한 세트로 함께 만들어진** 경로였다.

그럼 왜 안 보였나 — **마나 값이 한 번도 변한 적이 없어서** MP 게이지가 100/100에 고정돼 *멈춰* 보였을 뿐이다. 차감과 리젠이 생기자 같은 배선으로 실제로 움직였다.

> **"안 움직인다"는 "배선이 없다"가 아니다 — 입력이 안 변했을 수도 있다.**
>
> 그리고 같은 패밀리(HP↔MP)가 먼저 만들어져 있으면, **새 기능은 보통 거기 이미 끼어 있다.** 짓기 전에 있는지부터 확인하면 중복 구현을 피한다. (이전에 내가 "잔여: HUD 마나바"라고 적어 둔 메모도 이때 정정했다.)
