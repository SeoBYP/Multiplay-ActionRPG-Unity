# 챕터 23 학습 로그 — 전투 자원(마나) 서버 권위 + GameplayAbility 식별

> 스킬/회피에 **마나 비용**을 붙이는 작업에서 만난 세 가지 결정.
> ① **자원은 클라가 예측하되 서버가 게이트한다**(무한 시전 치팅 차단) — HP 권위와 닮았지만 *목적이 다르다*.
> ② **시간 비례 리젠은 동기화하지 않는다** — 같은 식이면 양쪽이 수렴하므로, 패킷은 "변곡점(차감/거부/입장)"에만.
> ③ "공격을 Ability로 만들어줘" / "HUD 마나바 만들어줘" 두 요청에서 배운 **YAGNI와 "만들기 전에 존재 확인"**.

---

## 1. 마나 = 서버 권위 + 클라 예측 — HP와 닮았지만 목적이 다르다

[챕터 21](./chapter-21-connection-liveness-hp-authority.md)에서 HP를 서버 권위로 올렸다(불사 핵 차단). 마나도 같은 골격(서버 권위 + 클라 예측)을 쓰지만 **존재 이유가 다르다**:

- **HP 권위** = 사망 판정을 서버가 직접 감지(클라가 "안 죽었다"고 거짓 보고하는 핵 차단).
- **마나 권위** = *발동 게이트*. 클라가 마나를 위조해 heavy/회피를 **무한 시전**하는 걸 서버가 막는다.

그래서 마나의 권위 지점은 "차감"이 아니라 **"발동 허가"**다.

```
입력(좌/우클릭·Ctrl)
  │
  ▼ 클라: ASC.Mana >= cost ? ──No──▶ 발동 안 함(송신도 안 함)  ← 손맛(즉각 거부)
  │Yes
  ├ 예측 차감(ApplyModifier −cost) + 애니 + C_Attack/C_Dodge 송신
  ▼
서버: Mana < cost ? ──Yes──▶ 발동 거부(데미지 0) ──┐
  │No                                              ├─▶ S_PlayerMana(owner) 정정
  ├ 쿨다운 게이트 통과 → 차감 ─────────────────────┘        ▼
  ▼                                          클라 EffectReceiver: ASC.Mana 덮어씀
적중/효과(기존 경로)
```

핵심은 **클라 예측과 서버 권위가 같은 상수**(`SkillTimeline.ManaCost`·`DodgeConfig.ManaCost`)를 본다는 점. 클라는 손맛을 위해 미리 깎고, 서버가 진실을 `S_PlayerMana`로 정정한다. 정상 플레이에선 둘이 같은 값 → 정정이 무해(idempotent). 위조 시에만 서버가 되돌린다.

> 회피 게이트는 한 발 더 — `TryBeginDodge(nowMs, manaCost)`를 **원자적**으로 만들었다. 쿨다운만 통과하고 마나가 모자라면 *무적·쿨다운을 아예 소모하지 않고* 거부한다. "절반만 발동"되는 상태를 없애려고 검증·차감·무적부여를 한 메서드에 묶었다.

## 2. 동기화 결정 — 리젠은 왜 안 보내나 (수렴 vs 스팸)

처음엔 "서버 권위니까 마나도 매 틱 owner에게 보내야 하나?"라고 생각했다. 그런데 마나는 **두 종류의 변화**가 있다:

- **이산적 변화**(차감/거부) — 발동 순간. 드물고, 정확해야 한다.
- **연속적 변화**(리젠) — 매 틱 조금씩. 잦지만, *시간 결정론*이다.

리젠을 매 틱(100ms) 보내면 owner 한 명에게 초당 10개 패킷이 흐른다 — 대역폭 낭비. 그런데 리젠은 `Mana += RegenPerSecond·dt`라는 **순수 함수**라, 클라와 서버가 *같은 rate*를 쓰면 굳이 안 보내도 같은 값으로 수렴한다(둘 다 max에서 clamp).

그래서 결정(사용자와 합의): **동기화 패킷은 차감/거부/입장 시점에만. 리젠은 양쪽이 동일 예측해 수렴.**

```
클라: PlayerCharacterAgent.Update → 매 프레임 Mana += rate·dt   (예측)
서버: RoomTickService → Room.RegenAllPlayerMana(dt)            (권위, 패킷 0)
       └ 둘 다 ManaConfig.RegenPerSecond=10 (Shared 단일소스) → 만마에서 일치
```

이걸 가능하게 한 건 **단일소스 상수**다. 리젠 rate를 `Shared.Gameplay/Combat/ManaConfig`에 한 번 정의하고 클라·서버가 같이 참조한다(`DodgeConfig` 형제). 한쪽만 바뀌면 수렴이 깨지므로, "예측 수렴"의 전제는 *수치가 진짜 단일소스*라는 것.

> 트레이드오프 명시: 정확도(매 틱 스트림)를 버리고 대역폭+단순성을 택했다. 비용은 "차감 직후~리젠 사이의 미세한 클라-서버 드리프트"인데, 만마로 수렴하고 발동 순간엔 `S_PlayerMana`로 정정되므로 *판정에 영향을 주는 지점*(발동 가부)에선 항상 서버가 맞다.

## 3. 베이스라인 일치 — 또 만난 "마지막 1마일"

마나도 챕터 21의 HP와 **똑같은 함정**이 있었다. 클라 프리팹 ASC는 `Mana(100,100)`인데, 서버 권위 `MaxMana`는 레벨테이블에서 온다(Lv1=50). 출발점이 다르면 클라는 "100 중 80"인데 서버는 "50 중 30"이라 발동 가부가 어긋날 수 있다.

해결도 HP와 같은 결: **입장 시 초기 `S_PlayerMana`를 owner에게 한 번 보내** 클라 ASC의 Max/Current를 서버 권위값으로 정렬한다(`RoomJoinLeaveHandler`). 이후엔 차감/거부 때만. 클라 `EffectReceiver`가 `SetMax`+`SetCurrent`로 베이스라인을 맞춘다.

```
서버 InitPlayerState(maxMana=레벨테이블 50)  ← PlayerStats.MaxMana→PlayerInfo→Room
입장 → S_PlayerMana{Mana 50, Max 50}
클라 ASC: SetMax(50)+SetCurrent(50)  ← 프리팹 100 베이스라인을 권위로 교정
```

> 교훈 재확인: "데이터가 흘러온 것"과 "판정 지점에 적용된 것"은 다르다. 마나도 MaxMana는 이미 GameServer가 계산하고 있었고, 빠진 건 *그걸 클라 ASC에 꽂는 한 줄*이었다.

## 4. "공격을 Ability로 만들어줘" — 엔진을 *안* 만든 이유

사용자가 "슬라임 공격들도 다 Ability로 만들고, 내가 어떤 GameplayAbility로 공격하는지 로그를 찍어줘"라고 했다. 처음엔 정식 GAS 엔진(`GameplayAbility.Activate/Commit/End`, `ASC.GrantAbility/TryActivate`)을 떠올렸다.

그런데 `gas-architecture.md`를 보니 **정식 어빌리티화는 의도적으로 CA-3로 보류**돼 있었다("확장점만 남기고 지금은 안 만든다"). 그리고 사용자가 실제로 원한 *관찰 가능한 결과*는 "어떤 어빌리티로 공격하는지 보이는 것"이었다.

여기서 두 범위를 사용자에게 제시하고 골랐다:

| 범위 | 내용 | 선택 |
|---|---|---|
| 경량 | AbilityId 식별 + 발동 로그(새 클래스/패킷 0, 로직 무변경) | ✅ |
| 정식 | Activate/Commit 엔진 + ASC 부여 + 스윙/스킬 전부 이관(클라+서버 광범위) | — (테스트 불가 상황 + YAGNI) |

경량을 골랐다. 알고 보니 **플레이어 공격은 이미 어빌리티**였다 — `SkillTimeline.Id`(basic_swing/heavy_swing)가 곧 AbilityId. 그래서 새 데이터 없이 `FireSkill`에서 발동 로그만 찍고, 슬라임엔 `attackAbilityId`(규약 `{monsterId}_attack`)를 붙여 로그를 통일했다.

```
플레이어: FireSkill(skillId) → [GameplayAbility] 발동: 'heavy_swing' (mana 20, cd 1200ms)
슬라임  : TryAttack       → [GameplayAbility] slime 발동: 'slime_attack' → dmg 9 +CC slow_3s
```

> 결정의 핵심: "Ability로 만든다"는 요청을 *엔진 신설*로 해석하지 않았다. 문서가 보류한 큰 구조 변경을, 테스트도 못 하는 시점에, 관찰 요구 하나 때문에 들이는 건 YAGNI 위반. **이름있는 식별 + 로그**로 요구를 정확히 충족하고 엔진 승격은 확장점으로 남겼다.

(부수: "데미지가 들어갔는지 안 보여" → `LocalCombat`에 스윙당 적중 수, `LocalMonster.TakeDamage`에 HP 변화/사망 로그를 넣어 헛스윙↔적중↔처치를 콘솔로 구분.)

## 5. "HUD 마나바 만들어줘" → 이미 있었다 (만들기 전에 존재 확인)

마나 코드를 깐 뒤 "HUD 마나바를 붙이자"는 다음 작업으로 잡았다. 그런데 막상 코드를 열어보니 **MVI 배선이 이미 전부 있었다**:

```
ASC.Mana 변화 → InGameModel.OnAttributeChanged(Mana) → InGameResult.MpChanged
   → InGameReducer.WithMp → InGameState.Mp/MaxMp → GameHud.mpSlider(MP_Ball).SetValue
```

HP/MP/버프가 **한 세트로 같이 만들어진** 경로였다. 그럼 왜 "안 보였나"? — **마나 차감/리젠을 넣기 전까진 마나 값이 한 번도 안 변해서** MP 공이 100/100에 고정돼 *멈춰* 보였을 뿐이다. 차감/리젠이 생기자 같은 배선으로 실제로 움직였다.

그래서 이 작업은 **코드 0줄**이 정답이었다. 중복 구현을 피하고, 내가 이전에 잘못 적어둔 "잔여: HUD 마나바" 메모를 문서에서 정정했다.

> 교훈: "이 기능 붙여줘"를 받으면 *짓기 전에 이미 있는지부터 본다*. 특히 같은 패밀리(HP↔MP)가 먼저 만들어진 경우, 새 기능은 보통 거기 이미 끼어 있다. "안 움직인다 ≠ 배선이 없다" — *입력이 안 변했을* 수도 있다.

## 처음 생각한 것 → 피드백으로 수정된 것

- **"마나도 서버가 매 틱 보내야지"** → 아니다. 리젠은 결정론이라 **같은 rate면 수렴** → 차감/거부/입장에만 동기화. 단일소스 상수가 전제.
- **"Ability로 만들어줘 = GAS 엔진 신설"** → 아니다. 문서가 CA-3로 보류한 영역. 관찰 요구는 **이름있는 식별+로그(경량)**로 충족, 엔진은 확장점.
- **"HUD 마나바 = 새로 배선"** → 이미 HP/MP 한 세트로 완비. 안 움직인 건 배선이 아니라 **값이 안 변해서**. 코드 0줄.
- **MaxMana 베이스라인** → HP와 같은 "마지막 1마일". 입장 시 `S_PlayerMana` 한 번으로 클라 ASC를 권위값에 정렬.

## 핵심 키워드

- **자원 권위의 목적 구분**: HP=사망 감지(불사 핵), 마나=발동 게이트(무한 시전 핵). 골격은 같아도 권위 지점이 다르다.
- **예측 수렴(deterministic regen)**: 연속 변화는 같은 식이면 안 보내도 수렴. 동기화는 *변곡점*에만. 전제=수치 단일소스(`ManaConfig`).
- **원자 게이트**: 검증+차감+효과부여를 한 메서드에. "절반 발동" 상태 제거(`TryBeginDodge(nowMs, manaCost)`).
- **베이스라인 일치(마지막 1마일)**: 클라 예측 출발점 = 서버 권위값. 입장 시 1회 정정 패킷.
- **YAGNI 해석**: "X로 만들어줘"를 최대 구조로 해석하지 않는다. *관찰 가능한 요구*를 최소 변경으로. 엔진은 확장점으로 보류.
- **만들기 전에 존재 확인**: 같은 패밀리가 먼저 있으면 새 기능은 거기 이미 끼어 있을 수 있다. "안 움직인다 ≠ 배선 없음".
