# 25. 락온 — 새 패킷 0개로 끝난 이유, 그리고 Unity의 `== null`이 한 거짓말

> **한 줄** — 락온은 "카메라 + 조준 + 동기화"를 한꺼번에 건드리는 큰 작업처럼 보인다. 그런데 **소유권을 먼저 따지자** 새 패킷도 서버 코드도 0줄이 됐다. 정작 위험했던 건 **Unity의 `== null`이 파괴된 객체를 null인 척 돌려주는** 함정이었고, 그건 사람이 아니라 테스트가 잡았다.
>
> **범위** 권위 판정과 네트워크 비용 · 이동/facing 축 분리 · 마커 레지스트리 · Unity fake null
> **결과** 서버 변경 0 · 새 패킷 0 · 클라 5파일

---

## 1. "패킷 0"의 근거 — 이 기능은 권위를 갖는가

처음 떠오른 그림은 "락온 상태를 서버에 보내고 서버가 조준을 고정한다"였다. 그전에 한 단계 앞선 질문을 했다.

> **락온은 게임 결과(데미지·적중)를 바꾸는가, 아니면 조준·연출인가?**

답은 **조준 보조**다. 적중 판정은 이미 **플레이어의 위치와 facing**으로 결정되고(던전=서버 히트박스, Main=`LocalCombat`), 그 facing은 **정지 중에도 이미 서버로 흐르고 있다**([08](./chapter-08-socket-movement.md)의 `C_Move`가 rotY를 싣는다).

그러면 결론이 따라온다.

```
락온이 해야 할 일 = 플레이어를 타겟 쪽으로 "회전"시키는 것. 그게 전부다.

  회전 → rotY 변경 → 기존 C_Move 송신 → 서버 히트박스가 자동으로 정렬   (던전)
  회전 → 같은 facing 으로 LocalCombat 판정                              (Main)

⇒ 새 패킷 없음. 서버 게이트 없음.
```

> **"이 기능을 네트워크로 보내야 하나?"의 답은 대개 "이 기능이 권위를 갖나?"에 달려 있다.** 락온은 권위가 없다 — 어디를 조준하든 클라의 자유다. 권위 있는 값(facing)은 *이미* 동기화되고 있었으므로, 락온은 **그 위에 올라타기만** 하면 됐다.
>
> 소유권을 먼저 따진 덕에 작업 범위가 "서버 + 프로토콜 + 클라"에서 **"클라 5파일"** 로 줄었다.

## 2. 축을 분리해 뒀더니 손맛이 공짜로 나왔다

소울류 락온의 손맛은 **"몸은 적을 보면서 이동은 좌우로 스트레이프"** 다. 이게 가능했던 이유는 모터가 이미 **이동 방향**과 **바라보는 방향**을 따로 계산하고 있었기 때문이다.

```
CharacterMotor.Move(input)
   ├─ DesiredMoveDirection   = 카메라 기준      ← 락온이 안 건드린다 → 스트레이프 유지
   └─ DesiredFacingDirection = 카메라 기준      ← 락온이 여기만 덮어쓴다
```

연결점은 **딱 두 개**였다.

```csharp
CharacterMotor.FacingOverride     // nullable — 값이 있으면 타겟 방향을 본다 (이동 무영향)
CharacterCameraFollow.LockTarget  // Transform — 값이 있으면 카메라 피벗이 타겟으로 수렴
```

`LockOnDriver`(순수 C#, `DodgeDriver`·`KnockbackDriver`와 같은 형제)가 매 프레임 이 둘에 값을 밀어 넣는다.

**상태머신에 락온 상태를 만들지 않았다.** 락온은 이동 모드가 아니라 그 위에 **직교하는 조준 보조**이기 때문이다([두 축 분리 원칙](../wiki/unity-gameplay-state.md)).

> 입력→이동을 한 덩어리로 짰다면 락온은 침습적 수술이 됐을 것이다. **이동과 facing을 애초에 분리해 둔 덕에** 한쪽만 nullable 오버라이드로 가로채는 변경이 됐다. 과거의 분리가 미래의 기능을 싸게 만든 사례다.

## 3. 마커 하나로 무관한 두 클래스를 통일

락온 대상은 두 종류다 — 던전 몬스터(`MonsterEntity`, 서버 보간)와 Main 몬스터(`LocalMonster`, 클라 시뮬). 클래스도 다르고 소유자도 다르다([16](./chapter-16-main-loot-path.md) 7절).

공통 인터페이스를 억지로 만드는 대신 **마커 컴포넌트 하나**(`LockOnTarget`, 정적 레지스트리)를 양쪽 프리팹에 붙였다.

```
LockOnDriver → 등록된 LockOnTarget 중 "화면 중앙에 가장 가까운 것" 선택
                 (WorldToViewportPoint — 물리 레이어를 모른다)
```

드라이버는 대상이 무엇인지 알 필요가 없다. **"락온될 수 있다"는 사실만 마커로 표시**하면 된다.

같은 틀을 부활에서도 썼다([24](./chapter-24-coop-revive.md) 4절의 `DownedAllyMarker`). **역할을 마커로 표시하고 레지스트리로 모으는 것**이 이 프로젝트의 반복 패턴이 됐다.

## 4. Unity의 `== null`은 거짓말을 한다

코드는 다 돌아가는 듯했는데 테스트 하나가 빨갛게 떴다 — `대상_소실시_자동_언락된다`.

원인은 한 줄이었다.

```csharp
public void Tick()
{
    if (_target == null) return;                    // ← 함정
    if (!IsTargetValid()) { ForceUnlock(); ... }
```

**Unity의 `==` 연산자는 파괴된 오브젝트를 null인 척 돌려준다.** C#의 진짜 null이 아닌데도 그렇다.

```
락온한 몬스터가 죽는다 → 오브젝트 Destroy
   → _target == null 이 true   (가짜 null)
   → 첫 줄에서 그냥 return
   → ForceUnlock() 을 건너뛴다
   → LockTarget 과 FacingOverride 가 풀리지 않는다
   ⇒ 카메라가 죽어 사라진 적의 자리에 영원히 잠긴다
```

수정은 **"미락(진짜 null)"과 "락 중인데 대상이 파괴됨(가짜 null)"을 구분하는 것**이었다.

```csharp
// LockOnDriver.cs:72
if (ReferenceEquals(_target, null)) return;   // 진짜 null = 애초에 락 안 함 → 할 일 없음
// 가짜 null(파괴됨)은 여기로 내려와 IsTargetValid() == false → ForceUnlock() 으로 정리
```

`ReferenceEquals`는 Unity의 연산자 오버로드를 **우회해 관리 참조 자체**를 본다. 락 중 파괴된 대상은 (가짜 null일 뿐) 관리 참조는 살아 있으므로 `ReferenceEquals`가 `false`를 반환하고, 정리 경로로 내려간다.

> **`obj == null`은 두 가지 다른 상태를 같은 답으로 뭉갠다** — "한 번도 할당된 적 없음"과 "있었는데 파괴됨". 대부분의 코드는 이 둘을 같게 다뤄도 되지만, **다르게 처리해야 하는 코드**(여기서는 "아무것도 안 함" vs "정리해야 함")에서는 반드시 갈라야 한다.
>
> 이건 Unity 게임플레이 코드 곳곳에 숨어 있는 함정이고, **증상이 항상 "정리가 안 됨"** 이라 원인을 찾기 어렵다.

수정 이유가 코드에 남아 있다 — `LockOnDriver.cs:70` 주석이 왜 `ReferenceEquals`인지 설명한다.

## 5. 이걸 잡은 건 사람이 아니라 테스트였다

```
LockOnDriverTests (PlayMode) — 4케이스
  FindBest는_화면중앙에_가까운_대상을_고른다
  락온_토글은_facing과_카메라를_잠그고_다시_해제한다
  사거리밖_대상은_락온되지_않는다
  대상_소실시_자동_언락된다              ← 이 하나가 fake null 을 잡았다
```

**손으로 플레이하며 발견했다면 "어, 카메라가 이상한데?"에서 원인까지 한참 걸렸을 것이다.** 이 테스트는 "락 → 타겟 Destroy → Tick → 풀렸는가"를 직접 단언하므로 실패 지점이 곧 원인이었다.

> 정리(cleanup) 로직은 **성공 경로를 아무리 돌려도 실행되지 않는다.** 그래서 "무엇이 해제되는가"를 별도로 단언하는 테스트가 필요하다. 같은 종류의 누락을 [04](./chapter-04-chat.md) 5절(`finally`가 종료 사유를 안 물었다)에서도 만났다.

## 6. 키를 추가하기 전에 기존 바인딩을 본다

처음 제안된 키는 `E`였다. 그런데 `E`는 이미 **Interact**(부활·줍기·대화)다. 한 번 누르면 **둘 다 발동**한다.

충돌 없는 `Tab`으로 확정했고, `.inputactions` → 생성 래퍼 → 액션까지 **정식 경로로 배선**했다(`PlayerInputActions`의 `LockOn` 액션 = `<Keyboard>/tab`).

> **키는 유한한 공간이고, 새 키를 더하는 일의 1단계는 "이미 무엇이 쓰고 있나"를 보는 것**이다. 상점을 `S`(후진)에 걸었다가 뺀 일도 있었다([18](./chapter-18-wallet-shop.md) 8절).
>
> 참고로 락온은 입력 파이프라인을 정석대로 통과했다 — 인벤토리 `I`키가 아직 `GameHud`에서 직접 폴링되는 것과 대조된다([15](./chapter-15-loot-drop-inventory.md) 8절). 같은 프로젝트에서 한쪽은 제대로 갔다.
