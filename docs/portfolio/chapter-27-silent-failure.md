# 27. 조용한 실패 — 완성됐다고 기록된 기능이 한 번도 실행된 적 없었다

> **한 줄** — "보스 애니가 잘 나오는지 확인만 하자"로 시작해서, **완성으로 기록된 기능 두 개가 실제로는 한 번도 실행된 적이 없었다**는 사실로 끝났다. 둘 다 버그가 아니었다 — 코드는 옳았고, 테스트는 초록이었고, 로그는 깨끗했다. **다만 아무 일도 일어나지 않았다.**
>
> **공통 원인** "없으면 아무것도 안 한다"를 **정상 동작으로 설계한 지점들** — 폴백·널 조건부(`?.`)·선택적 리소스
> **결론** **침묵은 성공과 구분되지 않는다.** 폴백을 두려면 대조 테스트를 짝으로 둬야 한다

---

## 1. 캡슐이 보스를 삼켰다

직전 작업에서 보스 강스킬 전용 애니를 넣었다. 체인을 하나씩 확인했더니 **전부 정상**이었다.

```
AnimationTriggerType.AttackSpecial(=9)                        ✓
CharacterAgentAnimations 의 트리거 필드                        ✓
Monster_leviathan_AC : AttackSpecial 상태 + AnyState 전이       ✓
Ability_leviathan_slam.cueTrigger = 9                          ✓
Monster_leviathan.prefab 트리거명 배선                          ✓
```

그런데 던전에서 **이 프리팹이 한 번도 스폰되지 않고 있었다.**

앞선 작업([26](./chapter-26-measured-combat-cleanup.md) 7절)에서 몬스터 변종을 별개 ID(`leviathan_boss`, `*_elite`)로 만들고 던전 스폰을 그 ID로 재배치했는데, **클라 표시 카탈로그에는 넣지 않았다.**

```
MonsterCatalogDefinition (스탯 · 서버 권위)   ← leviathan_boss 있음
MonsterVisualCatalog     (표시 · 클라 전용)   ← leviathan_boss 없음
                                                  ↓
                              GetPrefab() == null → 기본 캡슐 폴백
                                                  ↓
                              프리팹에 달린 AttackSpecial 배선 = 도달 불가
```

예외도, 에러 로그도, 경고도 없었다. **설계된 정상 경로**니까.

### 파급은 예상보다 컸다

등록돼 있던 원본 `leviathan`은 변종 전환 이후 **어느 던전도 스폰하지 않는다.** 즉 그 시점부터 **모든 던전에서 leviathan 모델이 뜬 적이 없었다.** 여러 던전의 보스·엘리트가 전부 캡슐이었다.

### 왜 아무도 몰랐나

두 카탈로그는 **다른 파일**이고 링크는 **문자열 ID**다. 컴파일러가 볼 수 없고, 기존 테스트 어디에도 **두 파일을 대조하는 지점이 없었다.**

## 2. 폴백의 짝은 "저작 시점 대조 테스트"다

수정 자체는 4줄(변종 → 원본 프리팹 매핑)이었다. 본론은 재발 방지다.

```
EditMode 대조 가드    저작 카탈로그의 모든 monsterId 가 표시 프리팹을 갖는가
                        (서버 픽스처 test_brute 만 명시 제외)

PlayMode 관통 가드    카탈로그 조회 → 프리팹 → AbilityCatalog(networkId 109)
                        → 라우터 → Animator 까지 실물로 관통
                        어느 고리가 끊겨도 여기서 잡힌다
```

### 가드가 실제로 잡는지도 실측했다

**"테스트를 추가했다"와 "그 테스트가 이 버그를 잡는다"는 다른 문장이다.** 수정을 되돌린 상태로 돌려 **`0/2 통과 · 2 실패`** 를 확인하고 복원했다.

> **미등록 시 조용한 폴백을 두는 순간, 저작 시점 대조 테스트가 그 폴백의 짝이 된다.** 둘 중 하나만 있으면 폴백은 안전장치가 아니라 **은폐 장치**다.

## 3. "없으면 아무것도 안 한다" ×2 — 완성된 툴이 무음이었다

어빌리티 연출 타임라인 툴은 **코드 100% 완료**로 기록돼 있었다. 실제로 소리를 내보니 **아무것도 안 났다.** 구멍이 둘이었고, 둘 다 침묵했다.

```
① Ability_*.cueEvents — 이벤트는 저작됐는데 sfxClip / vfxPrefab 이 전부 None
      → AbilityCuePlayer.Fire() 가 그냥 지나간다              (정상 동작)

② PlayerCharacter.prefab 에 AbilityCuePlayer 미부착
      → PlayerCharacterAgent 의 _cuePlayer?.Play(...) 가 통째로 스킵  (정상 동작)
```

**각각은 옳은 판단이었다.** `?.`은 "미배선 캐릭터에서 예외가 안 나게" 하려던 것이고, 리소스 선택성은 "카탈로그 id 폴백"을 위한 것이다.

문제는 **둘 다 실패를 침묵으로 바꾼다**는 점이고, 겹치면 기능이 사라진 걸 알 방법이 없다.

최소 배선(SFX 1개 + 컴포넌트 1개)으로 관통을 확인하고 `AudioSource.isPlaying`으로 **실제 재생**을 고정했다.

> **"설정이 있다"가 아니라 "소리가 났다"를 단언해야** 이 부류의 결함이 잡힌다. 이 구분이 [29](./chapter-29-multiplayer-sync-invisible-failures.md) 6절에서 다시 결정적으로 쓰인다 — "파라미터 검사 ≠ 재생 검증".

### 부수 수확 — 테스트 하네스도 잡음을 만든다

재생 검증에 플레이어 프리팹을 통째로 `Instantiate`했더니 DI가 없어 `Start()`가 NRE를 던졌고, Unity는 **그 로그만으로** 테스트를 실패시켰다. Cue 파이프와 무관한 잡음이다.

→ 재생은 **컴포넌트 단독**으로, 프리팹 부착 여부는 **별도 테스트**로 분리했다. **통합 대상을 넓게 잡으면 무관한 실패가 신호를 덮는다.**

## 4. 전체 스위트를 처음 돌렸다 — 필터 실행의 사각지대

검증 경로를 CLI로 세우면서 **PlayMode 전체 스위트를 처음 통째로** 돌렸다. **8건이 실패**했다.

### 먼저 한 일은 고치는 게 아니라 책임 소재 확정이었다

당일 변경을 `git stash`로 되돌려 같은 스위트를 다시 돌렸고, **동일한 8건이 동일하게 실패(177/185 일치)** 했다. **기존 결함으로 확정**한 뒤 착수했다.

> 이 순서가 중요하다. "내가 깬 것 같은데"로 시작하면 **원래 있던 결함을 내 변경 탓으로 오인**해 엉뚱한 곳을 되돌리게 된다. 추정 대신 실측으로 시작한 것이 이후 모든 판단의 근거가 됐다.

### 결과: 프로덕션 버그 0건

전부 **테스트가 코드·데이터 변화를 못 따라간** 경우였고, 유형이 5가지로 갈렸다.

| 유형 | 실체 | 왜 안 보였나 |
|---|---|---|
| 의존성 추가 미추종 | 프로덕션 타입이 생성자 의존을 얻은 날짜 > 테스트 최종 수정일 | **필터 실행만 해서** |
| 저작 데이터 하드코딩 | 스폰 좌표 `(2,0,0)` — 맵 재기획으로 Z가 −16 이동 | EditMode 쪽만 갱신됨 |
| Animator 판정 누락 | 블렌드 중에는 `GetCurrentAnimatorStateInfo`가 **이전 상태**를 반환 | 같은 파일의 콤보 테스트는 이미 올바른 헬퍼를 쓰고 있었다 |
| 프레임레이트 의존 | 모터는 실제 `Time.deltaTime` 기반인데 테스트는 고정 `0.02f`로 20프레임만 | 에디터가 빠를수록 덜 움직인다 |
| 보상 수치 하드코딩 | `exp == 20` — 몬스터 교체로 18이 됨 | 저작 SO·bake는 일치(**서버가 옳았다**) |

**세 번째와 네 번째가 뼈아프다.** 정답이 **같은 파일 안에 주석까지 달려** 있었는데 새로 추가된 테스트만 옛 방식으로 남아 있었다.

> **규칙을 문서에 적는 것과 헬퍼·린트로 강제하는 것은 다르다.** 옆줄에 정답이 있어도 새 코드는 그걸 안 본다.

프레임레이트 건은 더 깊은 얘기를 남겼다 — 모터가 `Time.deltaTime`을 **직접 읽는 것** 자체가, deltaTime을 인자로 받는 상태머신과 불일치다. 다만 프로덕션 시그니처를 바꾸면 이동 감각에 영향이 가므로 **이번엔 고치지 않고 기록만** 했다(테스트는 실시간 예산으로 돌려 증상만 제거).

## 5. 실패가 실패를 가린다 — 9번째 결함

8건을 고치자 **9번째가 나왔다.** `SocketSessionHeartbeatTests`가 실패하는데 **단독 실행하면 2/2 통과**였다.

원인은 **다른 테스트**였다.

```
UiInputCaptureBehaviourTests
   Player.Enable() 후 Disable() 없이 asset 파괴
   → Unity 가 누수 assert 로그를 띄운다
   → 그 로그가 "뒤이어 실행되는 무관한 테스트"에 붙어 실패시킨다
```

(같은 함정을 **다른 테스트 파일이 주석으로 경고**해 두고 있었다 — 4절과 같은 패턴이다.)

그동안 이게 안 보인 이유가 정확히 이것이다 — **기존 8건이 그 로그를 흡수하고 있었다.**

> **스위트가 부분 실패인 채로 방치되면 실패 개수는 결함 개수의 하한일 뿐이다.** 고칠수록 새 실패가 나오는 건 퇴보가 아니라 **가려진 것이 드러나는 정상 과정**이다. 전부 초록을 만들기 전까지는 몇 개인지 알 수 없다.

## 6. 무순서 Set 위의 페이징 — 진짜 전제는 정렬이었다

함께 정리한 부채(`GetRooms` 페이징)의 실체는 "필드가 없다"가 아니었다. **서버가 클라의 `room_count`를 완전히 무시하고 전체 활성 방을 반환**하고 있었다. 필드는 오래전부터 있었고 **읽는 코드만 없었다.**

> **계약이 있다고 지켜지는 게 아니다.** proto에 필드가 있다는 것과 서버가 그걸 본다는 것은 다른 사실이다.

구현하며 마주친 진짜 설계 지점은 페이징이 아니라 **정렬**이었다.

```
소스 = Redis room:active (Set — 무순서)
   → 정렬 없이 Skip/Take 하면
        · 같은 페이지를 두 번 불러도 다른 방이 나온다
        · 페이지 경계에서 방이 새거나 중복된다
```

**`offset`은 안정된 순서 위에서만 의미가 있다.** 서버가 `RoomId` 내림차순을 고정한 뒤에야 페이징이 성립한다.

판단이 코드에 남아 있다 — `DungeonLobbyService.cs:64` *"안정 정렬이 페이징의 전제다. 소스가 Redis Set(무순서)이라 정렬 없이 Skip/Take 하면…"*.

> 진짜 O(page)로 가려면 Set을 Sorted Set으로 옮겨야 하지만 **Redis 키 계약 변경**이라 보류하고, **줄어든 것(응답 크기·배치 쿼리 범위)과 남는 한계(리포지토리는 여전히 전량 조회)를 명시**했다.
>
> 같은 함정을 [03](./chapter-03-dungeon-lobby.md) 4절에서 이미 만났다 — "순서가 중요하면 순서를 저장하라".

곁가지로, 실패 `Result`에 `throw`하던 경로도 정리했다. **정상적인 실패 응답을 미처리 예외로 승격**시키고 있었다.

## 7. 저작과 bake 사이의 드리프트 — 그리고 그 후

이 프로젝트의 데이터 교리는 "SO 저작 → bake → 서버가 JSON을 읽는다"다. 중복 저작을 없애는 좋은 구조인데, **bake를 잊으면 조용히 갈라진다.**

정리 당시 실제로 벌어져 있었다.

| 값 | 클라 SO(저작) | 서버 bake(당시) |
|---|---|---|
| `basic_swing` startup/active | 167 / 125 | **200 / 100** |
| `leviathan_attack` | 213 / 87 | **200 / 100** |

`abilities.json`은 서버가 읽는 **판정 창·쿨다운의 권위**다. 클라가 167ms에 히트박스를 열고 서버는 200ms 기준으로 검증하면 던전에서 **데미지가 유실되거나 거부**될 수 있다.

같은 방식으로 `monsters.json`을 대조했더니 **불일치 0건**이었다 — 전면적 붕괴가 아니라 **한 파일만 갱신이 밀린** 상태였고, 그래서 더 안 보였다.

이 건은 당시 **고치지 않고 기록만** 했다. 값 자체가 저작자의 밸런스 결정이므로, 재Export는 그 결정을 서버에 반영하는 기계적 완결이지 임의 판단할 부분이 아니었기 때문이다.

### 현재 상태 — 해소됐다 (2026-08-22 확인)

```
abilities.json   basic_swing      startup 167 / active 125   ← SO 와 일치 ✅
                 leviathan_attack startup 213 / active  87   ← SO 와 일치 ✅
```

재Export가 이뤄져 두 값 모두 저작값과 맞다.

해소로 끝내지 않고 **감지 가드까지 세웠다.**

```csharp
// SocketServer.Tests/Combat/AbilityCatalogTests.cs:46
// bake 동기화 가드 — 서버 임베디드 abilities.json 이 클라 SO 저작값과 일치하는지 고정한다.
// ⚠️ 밸런스를 조정하면 Export 후 여기 기대값도 함께 갱신한다.
Assert.Equal(167, basic.Timeline.StartupMs);
Assert.Equal(125, basic.Timeline.ActiveMs);
```

원인도 특정됐다 — 타임라인 툴로 **SO만 바꾸고 Export를 안 돌린** 것이었다. 그리고 Export가 안 돌아간 이유가 9절 ②와 같은 계열이다: **Exporter 끝의 모달 팝업이 자동화를 블록**했다([26](./chapter-26-measured-combat-cleanup.md) 8절). 우회법(`BakeAll()` 직접 호출)을 확립했다.

> **다만 이 가드에는 한계가 있다** — 기대값이 하드코딩이라 **밸런스를 조정할 때마다 사람이 함께 갱신**해야 하고, 커버 범위도 `abilities.json` 하나다. 나머지 bake 산출물 5종(drop-tables·consumables·spawn-layouts·level-table·monsters)은 1회 대조로 드리프트 0을 확인했을 뿐 **상시 가드가 없다.**
>
> **"export 했나?"를 사람이 기억하는 구조는 반드시 한 번은 잊는다** — 그래서 저작→bake 파이프라인은 **드리프트 감지가 파이프라인의 일부**여야 한다.

| "8건 고치면 전부 초록" | **9번째가 나왔다** — 기존 실패가 다른 실패의 로그를 흡수하고 있었다 |
| "페이징 = offset/limit 추가" | 진짜 전제는 **정렬**. 무순서 Set 위의 offset은 중복·누락을 만든다 |
| "테스트 실패 = 프로덕션 버그" | 8건 전부 **테스트가 낡은 것**. 다만 그게 "문제 없음"은 아니다 — 실패한 테스트는 다른 결함을 가린다 |

---

### 이 챕터가 남긴 규칙

| 규칙 | 이유 |
|---|---|
| 폴백에는 **저작 시점 대조 테스트**를 짝으로 | 없으면 폴백이 은폐 장치가 된다 |
| "설정이 있다"가 아니라 **"실제로 일어났다"**를 단언 | 침묵은 성공과 구분되지 않는다 |
| 스위트는 **전부 초록**으로 유지 | 부분 실패는 다른 실패를 흡수한다 |
| 실패를 만나면 **책임 소재부터 실측** | 추정으로 시작하면 엉뚱한 곳을 되돌린다 |
| 통합 테스트의 **대상을 좁게** | 무관한 실패가 신호를 덮는다 |
