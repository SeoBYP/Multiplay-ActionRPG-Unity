# 챕터 27 학습 로그 — 조용한 실패: 폴백·기본값·필터 실행이 기능을 삼킨 날

> 이 트랙은 "보스 슬램 애니가 잘 나오는지 확인만 하자"로 시작해서, **완성됐다고 기록된 기능 두 개가 실제로는 한 번도 실행된 적이 없었다**는 사실로 끝났다.
> 둘 다 버그가 아니었다. 코드는 옳았고, 테스트는 초록이었고, 로그는 깨끗했다. 다만 **아무 일도 일어나지 않았다.**
>
> 공통 원인은 하나다: **"없으면 아무것도 안 한다"를 정상 동작으로 설계한 지점들.**
> 폴백(fallback)·널 조건부(`?.`)·선택적 리소스는 전부 견고함을 위해 넣은 장치인데, 데이터가 한쪽만 갱신되는 순간 **기능이 통째로 사라져도 아무 신호가 없다.**
>
> 요약하면: **침묵은 성공과 구분되지 않는다. 폴백을 두려면 대조 테스트를 짝으로 둬야 한다.**

---

## 1. 캡슐이 보스를 삼켰다 — 설계된 폴백이 기능을 지운다

직전 작업에서 보스 강스킬 전용 애니(`AttackSpecial`)를 넣었다. 체인을 하나씩 확인했더니 전부 정상이었다.

```
AnimationTriggerType.AttackSpecial(=9)            ✓
CharacterAgentAnimations.m_animationAttackSpecialTrigger  ✓
Monster_leviathan_AC: AttackSpecial 상태 + AnyState 전이(hasExitTime=false)  ✓
Ability_leviathan_slam.cueTrigger = 9             ✓
Monster_leviathan.prefab 트리거명 배선            ✓
```

그런데 던전에서 이 프리팹이 **한 번도 스폰되지 않고 있었다.**

앞선 작업(AC-G)에서 몬스터 변종을 별개 ID(`leviathan_boss`, `*_elite`)로 만들고 던전 스폰을 그 ID로 재배치했는데, **클라 표시 카탈로그(`MonsterVisualCatalog`)에는 넣지 않았다.** 스포너는 미등록이면 기본 캡슐로 폴백한다 — 예외도, 에러 로그도, 경고도 없다. **설계된 정상 경로**니까.

```
MonsterCatalogDefinition (스탯·서버 권위)   ← leviathan_boss 있음
MonsterVisualCatalog     (표시·클라 전용)   ← leviathan_boss 없음
                                              ↓
                        GetPrefab() == null → 기본 캡슐 폴백 (조용히)
                                              ↓
                        프리팹에 달린 AttackSpecial 배선 = 도달 불가
```

파급은 예상보다 컸다. 등록돼 있던 `leviathan`은 AC-G 이후 **어느 던전도 스폰하지 않는다.** 즉 그 시점부터 **모든 던전에서 leviathan 모델이 뜬 적이 없었다.** dungeon_02/04/05(boss)·03/04/05(elite) 전부 해당.

**왜 아무도 몰랐나**: 두 카탈로그는 **다른 파일**이고 링크는 **문자열 ID**다. 컴파일러가 볼 수 없고, 기존 테스트 어디에도 두 파일을 대조하는 지점이 없었다.

수정은 4줄(변종 → 원본 프리팹 매핑)이었지만, 재발 방지가 본론이다:

- **EditMode 대조 가드** — 저작 카탈로그의 모든 monsterId가 표시 프리팹을 갖는가(서버 픽스처 `test_brute`만 명시 제외).
- **PlayMode 관통 가드** — 카탈로그 조회 → 프리팹 → `AbilityCatalog`(networkId 109) → 라우터 → Animator 전 구간을 실물로 관통. 어느 고리가 끊겨도 여기서 잡힌다.

가드가 실제로 잡는지도 **실측**했다. 수정을 되돌린 상태로 돌려 `0/2 통과·2 실패`를 확인하고 복원했다. "테스트를 추가했다"와 "그 테스트가 이 버그를 잡는다"는 다른 문장이다.

> 교훈: 미등록 시 조용한 폴백을 두는 순간, **저작 시점 대조 테스트가 그 폴백의 짝**이 된다. 둘 중 하나만 있으면 폴백은 안전장치가 아니라 은폐 장치다.

## 2. 완성된 툴이 무음이었다 — "없으면 아무것도 안 한다" ×2

어빌리티 연출 타임라인 툴은 코드 100% 완료로 기록돼 있었다(P0~P8 + 개선 백로그 W1~W8). 실제로 소리를 내보니 **아무것도 안 났다.** 구멍이 둘이었고, 둘 다 침묵했다.

```
① Ability_*.cueEvents  — 이벤트는 저작됨, sfxClip/vfxPrefab 이 전부 None
     → AbilityCuePlayer.Fire() 가 그냥 지나감 (정상 동작)
② PlayerCharacter.prefab — AbilityCuePlayer 미부착
     → PlayerCharacterAgent 의 `_cuePlayer?.Play(...)` 가 null 조건부로 통째 스킵 (정상 동작)
```

`?.`은 "미배선 캐릭터에서 예외 안 나게" 하려고 넣은 것이고, 리소스 선택성은 "카탈로그 id 폴백"을 위해 넣은 것이다. 각각은 옳은 판단이다. 문제는 **둘 다 실패를 침묵으로 바꾼다**는 점이고, 겹치면 기능이 사라진 걸 알 방법이 없다.

최소 배선(SFX 1개 + 컴포넌트 1개)으로 관통을 확인하고 `AudioSource.isPlaying`으로 **실제 재생**을 고정했다. "설정이 있다"가 아니라 "소리가 났다"를 단언해야 이 클래스의 결함이 잡힌다.

**부수 수확 — 테스트 하네스 함정**: 재생 검증에 플레이어 프리팹을 통째로 `Instantiate`했더니 DI가 없어 `CharacterAgent.Start()`가 NRE를 던졌고, Unity는 그 **로그만으로** 테스트를 실패시켰다. Cue 파이프와 무관한 잡음이다. → 재생은 컴포넌트 단독으로, 프리팹 부착 여부는 별도 테스트로 분리했다. **통합 대상을 넓게 잡으면 무관한 실패가 신호를 덮는다.**

## 3. 전체 스위트를 처음 돌렸다 — 필터 실행의 사각지대

이번에 Unity CLI로 검증 경로를 세우면서 **PlayMode 전체 스위트를 처음 통째로** 돌렸다. 8건이 실패했다.

먼저 한 일은 고치는 게 아니라 **책임 소재 확정**이었다. 당일 변경을 `git stash`로 되돌려 같은 스위트를 다시 돌렸고, **동일한 8건이 동일하게 실패(177/185 일치)** 했다. 기존 결함으로 확정한 뒤 착수했다.

결과: **프로덕션 버그 0건.** 전부 테스트가 코드·데이터 변화를 못 따라간 경우였고, 유형이 5가지로 갈렸다.

| 유형 | 실체 | 왜 안 보였나 |
|---|---|---|
| 의존성 추가 미추종 | 프로덕션 타입이 생성자 의존을 얻은 날짜 > 테스트 최종 수정일 | 필터 실행만 해서 |
| 저작 데이터 하드코딩 | 스폰 좌표 `(2,0,0)` — 맵이 재기획으로 Z-16 이동 | EditMode 쪽만 갱신됨 |
| Animator 판정 누락 | 블렌드 중엔 `GetCurrentAnimatorStateInfo`가 **이전 상태**를 반환 | 같은 파일 콤보 테스트는 이미 올바른 헬퍼 사용 |
| 프레임레이트 의존 | `CharacterMotor.Move`는 실제 `Time.deltaTime` 기반인데 테스트는 고정 `0.02f`로 20프레임만 | 에디터가 빠를수록 덜 움직임 |
| 보상 수치 하드코딩 | `exp == 20` — 몬스터 교체로 18이 됨 | 저작 SO·bake는 서로 일치(서버가 옳았다) |

특히 세 번째와 네 번째가 뼈아프다. **정답이 같은 파일 안에 주석까지 달려 있었는데** 새로 추가된 테스트만 옛 방식으로 남아 있었다. 규칙을 문서에 적는 것과 **린트·헬퍼로 강제**하는 것의 차이다.

프레임레이트 의존 건은 더 깊은 얘기를 남겼다. `CharacterMotor.Move`가 `Time.deltaTime`을 **직접 읽는 것** 자체가 deltaTime을 인자로 넘기는 상태머신과 불일치다. 다만 프로덕션 시그니처를 바꾸면 이동 감각에 영향이 가므로 이번엔 **고치지 않고 기록만** 했다. 테스트를 실시간 예산으로 돌려 증상은 없앴고, 구조 문제는 별도 논의로 남겼다.

## 4. 실패가 실패를 가린다 — 9번째 결함

8건을 고치자 **9번째**가 나왔다. `SocketSessionHeartbeatTests`가 실패하는데 **단독 실행하면 2/2 통과**였다.

원인은 다른 테스트였다. `UiInputCaptureBehaviourTests`가 `PlayerInputActions.Player.Enable()` 후 `Disable()` 없이 asset을 파괴해, Unity가 띄우는 **누수 assert 로그가 그 뒤에 실행되는 무관한 테스트에 붙어** 실패시키고 있었다. (같은 함정을 다른 테스트 파일이 주석으로 경고해 두고 있었다.)

그동안 이게 안 보인 이유가 정확히 이것이다 — **기존 8건이 그 로그를 흡수하고 있었다.** 실패가 실패를 가리면, 고칠수록 새 실패가 나온다. 이건 퇴보가 아니라 **가려진 것이 드러나는 정상 과정**이다.

> 교훈: 스위트가 부분 실패인 채로 오래 방치되면 실패 개수는 결함 개수의 **하한**일 뿐이다. 전부 초록을 만들기 전까지는 몇 개인지 알 수 없다.

## 5. 무순서 Set 위의 페이징 — 정렬이 기능의 전제일 때

같이 정리한 부채 하나(`GetRooms` 페이징)는 성격이 달랐지만 교훈이 이어진다.

부채의 실체는 "필드가 없다"가 아니라 **서버가 클라의 `room_count`를 완전히 무시하고 전체 활성 방을 반환**하던 것이었다. 필드는 오래전부터 있었고, 읽는 코드만 없었다. 계약이 있다고 지켜지는 게 아니다.

구현하며 마주친 진짜 설계 지점은 페이징이 아니라 **정렬**이었다:

```
소스 = Redis `room:active` (Set — 무순서)
      → 정렬 없이 Skip/Take 하면
        · 같은 페이지를 두 번 불러도 다른 방이 나온다
        · 페이지 경계에서 방이 새거나 중복된다
```

`offset`은 **안정된 순서** 위에서만 의미가 있다. 서버가 `RoomId` 내림차순(최신 먼저)을 고정한 뒤에야 페이징이 성립한다. 진짜 O(page)로 가려면 Set을 Sorted Set으로 옮겨야 하지만 Redis 키 계약 변경이라 보류하고, **줄어든 것(응답 크기·플레이어/유저 배치 쿼리 범위)과 남는 한계(리포지토리는 여전히 전량 조회)를 문서에 명시**했다.

부수적으로, 실패 `Result`에 `throw new InvalidOperationException`하던 경로도 정리했다. **정상적인 실패 응답을 미처리 예외로 승격**시키고 있었다.

## 6. 저작과 bake 사이 — 아직 열려 있는 조용한 드리프트

이 프로젝트의 데이터 교리는 "SO로 저작 → bake → 서버가 JSON을 읽는다"이다. 중복 저작을 없애는 좋은 구조인데, **bake를 잊으면 조용히 갈라진다.**

정리 중 실제로 벌어져 있었다:

| 값 | 클라 SO(저작) | 서버 bake |
|---|---|---|
| `basic_swing` startup/active | **167 / 125** | 200 / 100 |
| `leviathan_attack` | **213 / 87** | 200 / 100 |

`abilities.json`은 서버가 읽는 **판정 창·쿨다운의 권위**다. 클라가 167ms에 히트박스를 열고 서버는 200ms 기준으로 검증하면 던전에서 데미지가 유실되거나 거부될 수 있다. 같은 방식으로 `monsters.json`을 대조했더니 **불일치 0건**이었다 — 즉 이건 전면적 붕괴가 아니라 **한 파일만 갱신이 밀린** 상태다. 그래서 더 안 보인다.

(이 건은 이번 트랙에서 **고치지 않고 기록만** 했다. 값 자체는 저작자의 밸런스 결정이므로, 재Export는 그 결정을 서버에 반영하는 기계적 완결이지 내가 임의로 판단할 부분이 아니다.)

> 교훈: 저작→bake 파이프라인은 **드리프트 감지가 파이프라인의 일부**여야 한다. 사람이 "export 했나?"를 기억하는 구조는 반드시 한 번은 잊는다.

|---|---|
| "보스 애니 배선 확인만 하면 끝" | 배선은 전부 정상이었고, **그 프리팹이 스폰조차 안 되고 있었다** |
| "툴이 코드 100% 완료면 동작한다" | 리소스 미할당 + 컴포넌트 미부착으로 **무음**. 완료의 정의에 "실행됨"이 빠져 있었다 |
| "PlayMode 실패 8건은 내가 깬 것일 수도" | stash 되돌림으로 **동일 실패 실측** → 기존 결함 확정. 추정으로 넘기지 않은 게 이후 판단의 근거가 됐다 |
| "8건 고치면 전부 초록" | **9번째가 나왔다** — 기존 실패가 다른 실패의 로그를 흡수하고 있었다 |
| "페이징 = offset/limit 추가" | 진짜 전제는 **정렬**. 무순서 Set 위의 offset은 페이지 간 중복·누락을 만든다 |
| "테스트 실패 = 프로덕션 버그" | 8건 전부 **테스트가 낡은 것**. 다만 그게 "문제 없음"은 아니다 — 실패한 테스트는 다른 결함을 가린다 |
