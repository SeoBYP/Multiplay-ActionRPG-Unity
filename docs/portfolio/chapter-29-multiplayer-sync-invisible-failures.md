# 29. 멀티플레이 동기화 — 안 보이는 것은 왜 안 보이는가

> **한 줄** — "던전에서 서로의 애니메이션이 동기화되게 해줘"로 시작해서, **동기화 코드가 아니라 그 앞뒤에서** 네 번 막혔다. 네 번 다 증상은 "화면에 안 나온다"였는데 원인은 전부 다른 층에 있었다 — 프리팹 배선, **전투 권위**, 세션 수명, 애니메이터 전이.
>
> **공통점** 전부 **에러가 없었다.** 예외도 경고도 실패한 테스트도 없이 조용히 아무 일도 안 일어났다
> **결론** **동기화는 보내는 쪽 코드가 아니라, 받는 쪽에서 그 값이 실제로 소비되는지까지가 기능이다**

---

## 1. 패킷 설계의 첫 질문 — 역산 가능한가

원격 플레이어가 옆걸음을 쳐도 다른 화면에선 전부 전진으로 보였다. 원격이 8방향 블렌드를 안 쓰고 1D 트리만 돌리고 있었기 때문이다.

"방향을 패킷에 넣자"가 첫 생각이었는데, 넣기 전에 **이미 보내고 있는 것**을 먼저 셌다.

```
이미 흐르는 것:  위치(PosX/Y/Z) → 시간 미분 → 속도
                회전(RotY)      → facing
        조합  →  로컬과 같은 공식으로 MoveX/MoveY 복원   ⇒ 추가 바이트 0
```

반면 점프·낙하·사다리는 **전부 "y가 변한다"** 로 같아서 위치만으로는 원리적으로 구분되지 않는다. **그것만 실었다.**

| 항목 | 결정 | 근거 |
|---|---|---|
| 8방향 | **안 보냄**(역산) | 위치 + 회전에 이미 들어 있다 |
| 로코모션 모드 | `byte AnimState` 추가 | 역산이 **원리적으로 불가능** |
| 회피 방향 | 이동 스트림이 아니라 **회피 이벤트**에 | 1회성 신호를 상시 스트림에 실을 이유가 없다 |

`C_Move`는 **최고빈도 패킷**이라 여기 붙는 1바이트는 계속 비용이 된다. **"역산 가능한가"를 먼저 묻는 것**이 패킷 계약을 늘리기 전의 기본 질문이 됐다.

> 같은 질문을 [25](./chapter-25-lock-on-targeting.md) 1절에서도 했다 — 그때는 "권위를 갖는가"였고 이번엔 "역산 가능한가"다. **둘 다 "새 필드를 만들기 전에 이미 있는 것을 세는" 습관**이다.

## 2. 서버는 이 값을 해석하지 않는다

`AnimState`의 enum을 **서버에 두지 않았다.** 서버는 불투명 byte로 릴레이만 한다.

```csharp
// MovementHandler.cs:30
// AnimState 는 해석 없이 그대로 옮긴다: 연출은 클라 권위이고 서버는 중계만 한다.
```

**서버가 상태를 해석하기 시작하면 클라 FSM과 진실원이 둘이 된다.** 클라가 상태를 하나 추가할 때마다 서버도 알아야 하고, 둘이 어긋나면 어느 쪽이 옳은지 판정할 근거가 없다.

서버가 모르는 값(200)이 와도 그대로 흘려보내는 것을 **테스트로 고정**했다(`C_Move_라운드트립시_AnimState가_보존된다`).

## 3. 첫 번째 조용한 실패 — 파라미터명이 비어 있었다

구현을 끝내고 테스트를 돌리니 3건이 실패했다. 원인은 내 코드가 아니라 **프리팹**이었다.

```
RemotePlayerCharacter.prefab
  m_animationMoveXFloat:  ''      ← 비어 있음
  m_animationMoveYFloat:  ''
  m_animationStrafeBool:  ''
  m_animationJumpTrigger: ''      ... 총 6개
```

애니메이션 어댑터는 **파라미터명이 비면 `SetFloat`/`SetTrigger`를 조용히 스킵**한다. 예외도 경고도 없다.

원격은 원래 `Speed` 하나만 썼고 그건 배선돼 있었으니, **나머지가 비어 있어도 아무 증상이 없었다.**

> 여기서 배운 건 기법이 아니라 **순서**다. **테스트를 먼저 썼기 때문에** 구현 직후에 잡혔다. 나중에 썼다면 "내 구현이 틀렸나"를 한참 들여다봤을 것이다.
>
> 같은 부류를 [27](./chapter-27-silent-failure.md)에서 정리했는데, 이번에 목록에 **"소비되지 않은 파라미터"** 가 추가됐다.

## 4. 두 번째 — 사망 연출이 안 보인 진짜 원인은 전투 권위였다

사망 연출이 자기 화면에서만 나왔다. 첫 가설은 **"내가 방금 켠 Jump/Fall/Land 트리거가 Dead 포즈를 밀어냈다"** 였다.

**회귀 테스트 3건을 먼저 짜서 확인했더니 전부 통과** — 가설이 틀렸다.

그래서 **로그를 셌다.**

```
양쪽 클라 로그    S_PlayerDead 수신  = 0건 (전 세션)
서버 로그         몬스터 → user1 공격 = 7회
클라 로그         로컬 HP 피해 적용    = 14회      ← 정확히 2배
```

**차액의 정체는 아군 오사였다.** 피해 수치도 갈렸다 — 몬스터는 `-16/-18`(스탯 산식), 정체불명은 `-10/-15`(어빌리티 플랫값).

```
플레이어 A 공격 → 사거리 안의 아군 B 선택
   ├─▶ S_ApplyEffect{Target=B, -10} 브로드캐스트  → 클라 B: HP 깎임   ✅
   └─▶ (서버 측 B.Hp 차감 없음)                   → 서버 B.Hp: 그대로 ❌

⇒ 클라가 먼저 0 → 로컬 사망 애니만 재생
⇒ 서버는 살아 있다고 봄 → S_PlayerDead 영영 미발행 → 원격은 계속 서 있음
```

**코드 주석이 원인을 그대로 적어두고 있었다** — `// 플레이어 HP 권위는 클라(결정론 lite) — 서버가 모른다`.

HP를 서버 권위로 승격할 때([21](./chapter-21-connection-liveness-hp-authority.md)) **몬스터→플레이어 경로만** 옮겨졌고, **플레이어→플레이어는 옛 방식으로 남아 있었다.** 평소엔 아군 오사가 눈에 안 띄어 드러나지 않다가, 둘이 붙어 콤보를 돌리자 갈라졌다.

> **권위를 옮길 때는 "그 값을 바꾸는 모든 경로"를 세어야 한다.** 하나만 남아도 두 값은 **반드시** 갈라지고, 갈라진 뒤엔 그 값에 걸린 **모든 판정(사망·다운·부활·던전 실패)이 조용히 멈춘다.**

### 해결은 코드가 아니라 게임 규칙에서 나왔다

**아군 오사 제거.** Co-op PvE라 플레이어 공격이 플레이어를 대상으로 삼을 이유가 없다.

```csharp
// CombatHandler.cs:130-136
// 아군 오사 없음 — Co-op PvE 라 플레이어 공격은 플레이어를 대상으로 삼지 않는다.
// … 아군 오사를 없애면 "클라만 깎는 HP" 경로 자체가 사라져 두 값이 항상 일치한다.
```

**버그를 고친 게 아니라 버그가 살 수 있는 경로를 없앴다.** (PvP를 넣는다면 반드시 서버 차감을 동반해야 한다는 경고를 코드에 남겼다.)

## 5. 세 번째 — 재입장 30회 거절, 그리고 내가 먼저 내놓은 틀린 설명

던전 플레이 중 Play를 껐다 켜면 `방 입장 실패 (시도 N/30)`이 30줄 쌓였다. 서버 사유는 `Room is full`.

여기서 **틀린 설명을 먼저 내놨다** — "재접속 유예(60s)가 슬롯을 물고 있다". 시각을 맞춰보니 아니었다.

```
15:39:34  마지막 패킷 수신
15:39:35  Play 정지 — 소켓이 FIN 없이 사라짐
15:39:40  재입장 시도 → "Room is full" × 30
15:40:37  서버가 유휴 타임아웃으로 죽음 감지        ← 63초 걸림
15:41:37  그제서야 재접속 유예 만료
```

**슬롯을 막은 건 유예 장부가 아니라 "아직 죽은 줄 모르는 세션"이었다.** 유예는 그 뒤에야 시작된다.

> 원인을 잘못 짚었으면 "유예 중 세션을 정원에서 빼기"를 고쳤을 텐데, **그건 이 케이스를 전혀 못 고친다.** 감지 자체가 아직 안 됐기 때문이다.
>
> 이 63초는 [21](./chapter-21-connection-liveness-hp-authority.md) 8절에서 고른 상수(타임아웃 60s + 스윕 15s)의 청구서다.

**실제 해결은 재접속 인수(takeover)** 다 — 같은 UserId가 들어오면 옛 세션을 비우고 자리를 넘겨받는다. **감지 전이든 유예 중이든 둘 다 덮인다.**

```csharp
// RoomManager.cs:105 — 같은 UserId 의 옛 세션이 방에 남아 있으면 자리를 비운다(재접속 인수)
// :121  "Room {RoomId} takeover — old session {OldSessionId} evicted for {NewSessionId}"
```

비울 때 `graceful: true`를 쓰는 게 핵심이다 — **세션만** 교체하고 `PlayerState`(위치·HP)는 보존해야 원래 자리로 복귀한다([08](./chapter-08-socket-movement.md) 2절에서 상태를 방에 둔 결정이 여기서 값을 한다).

### 같이 고친 두 가지

**① 진단 정보를 버리고 있었다.** 서버는 `S_PlayerJoined.Message`에 사유를 담아 보내는데 클라는 `Success`만 보고 버렸다. 그래서 콘솔에는 `state=Failed` 30줄만 남고 원인을 알 수 없었다.

```csharp
// SocketSession.cs:187
LastJoinFailureReason = joined.Success ? null : joined.Message;
```

> **진단 정보를 버리는 것도 결함이다.** 서버가 이유를 말해주는데 클라가 안 듣고 있었다.

**② 재시도 예산이 서버 유예보다 짧았다**(30s vs 60s). **기다리는 쪽이 먼저 포기하면 기다리는 의미가 없다.**

사유 분기에서 한 가지 판단 — **모르는 사유는 재시도가 기본값**이다. 서버 문구가 바뀌었을 때 **조용히 포기하는 쪽이 헛도는 것보다 나쁘다.**

## 6. 네 번째 — 내가 고친 것이 다음 것을 부쉈다

세 번째를 고치는 과정에서 "블렌드 중 AnyState 트리거가 삼켜진다"를 발견하고 `interruptionSource`로 풀었다. 그러자 **걷기·달리기가 아예 안 나왔다.**

```
frame  0: cur=Locomotion → StrafeLocomotion  inTransition=True  normTime=0.02
frame 39: cur=Locomotion → StrafeLocomotion  inTransition=True  normTime=0.03   ← 0.67초 뒤에도 그대로
```

Unity는 인터럽트가 켜진 전이의 **소스 상태 전이를 다시 평가**한다. 조건이 계속 참이니 **같은 전이가 매 프레임 자기 자신으로 재시작**한다 — 목적지에 영영 도달하지 못한다.

해결은 인터럽트가 아니라 **전이 창 자체를 없애는 것**(`duration 0`)이었다. **창이 없으면 트리거가 삼켜질 구간도 없다.**

> **프레임워크의 "옵션 하나로 푸는" 해법을 쓸 때는 그 옵션의 재평가 규칙까지 알아야 한다.** 모르면 창을 없애는 쪽이 안전하다 — **없는 창은 어떤 규칙으로도 재평가되지 않는다.**

## 7. 왜 213개 테스트가 이걸 전부 통과시켰나

가장 뼈아픈 부분이다. **Walk/Run이 안 나오는 상태에서 PlayMode 213개가 전부 초록**이었다.

이유는 단순하다. 애니 테스트가 전부 **파라미터 값**만 봤다.

```csharp
❌ Assert.Greater(animator.GetFloat("MoveX"), 0.5f)   // 값은 들어갔다
✅ Assert.IsTrue(info.IsName("StrafeLocomotion"))      // 그 값을 소비해 상태에 도달했나
✅ Assert.Greater(after.normalizedTime, before)        // 그 상태에서 시간이 흐르나
```

**"값을 넣었다"와 "그 값이 재생으로 이어졌다" 사이에 상태 머신이라는 층이 통째로 빠져 있었다.**

새 테스트는 그 층을 본다(`ActionRootTests`·`PlayerLocomotionAnimTests`·`RemoteDriverAnimTests` 등 5개 파일이 `IsName`/`normalizedTime`으로 재생을 단언한다).

### 그 테스트가 정말 이 버그를 잡는지 실측했다

컨트롤러에 **고장을 주입해 2/2 실패**를 확인하고 복구했다. [27](./chapter-27-silent-failure.md) 2절에서 배운 것("테스트를 추가했다 ≠ 그 테스트가 이 버그를 잡는다")을 이번엔 **처음부터** 적용했다.

부수적으로 하네스 함정도 다시 밟았다 — 캐릭터 프리팹을 통째로 Instantiate했더니 DI 없는 컴포넌트가 NRE를 던졌고, **그 로그가 테스트를 실패시켜 진짜 신호를 덮었다.** 컨트롤러만 단독으로 굴리도록 좁혀 해결했다. **챕터 27과 같은 결론에 다른 경로로 도착했다.**

## 8. 남은 것

- 원격 사다리는 배속을 목표 y 변화로 근사한다 — 아주 짧은 오르내림에서 실제 클립 속도와 미세하게 어긋날 수 있다(**미실측**).
- 재접속 인수는 **같은 UserId만** 허용한다. 한 계정 다중 로그인 정책이 생기면 이 규칙을 다시 봐야 한다.
- `LastJoinFailureReason`은 로그·분기까지만 쓴다. 사용자에게 보여줄 UI 문구는 별건이다.

## 처음 생각한 것 → 데이터가 뒤집은 것

| 처음 | 실제 |
|---|---|
| "방향을 패킷에 넣어야 한다" | 위치+회전에 **이미 들어 있다**. 넣을 것은 역산 불가능한 **모드 1바이트**뿐 |
| "서버도 상태 enum을 알아야 한다" | 서버가 해석하면 **진실원이 둘**이 된다. 불투명 릴레이 |
| "사망 연출이 안 나오는 건 연출 문제" | 연출은 멀쩡했다. **서버가 죽은 걸 몰랐다** |
| "내가 켠 트리거가 Dead를 밀어냈다" | 회귀 테스트 3건으로 **가설 기각** → 그다음 로그를 셌다(7 vs 14) |
| "재접속 유예가 슬롯을 막는다" | **아직 죽은 줄 모르는 세션**이 막았다(감지 63초). 잘못 짚었으면 엉뚱한 걸 고칠 뻔했다 |
| "트리거 유실은 interruptionSource로" | 전이가 **자기 자신으로 재시작**해 Walk/Run이 사라졌다. 창을 없애는 게 답 |
| "213개가 초록이면 안전하다" | 전부 **파라미터만** 봤다. 상태 도달·재생 진행은 아무도 안 봤다 |

### 이 챕터가 남긴 것

| 규칙 | 이유 |
|---|---|
| 새 필드 전에 **"역산 가능한가"** | 최고빈도 패킷의 1바이트는 영구 비용이다 |
| 연출은 클라 권위 — 서버는 **불투명 릴레이** | 해석하는 순간 진실원이 둘이 된다 |
| 권위 이전 시 **모든 경로를 센다** | 하나만 남아도 값은 반드시 갈라진다 |
| **가설은 테스트로 먼저 기각**한다 | 그래야 로그를 셀 이유가 생긴다 |
| 진단 정보를 **버리지 않는다** | 서버가 말해주는 이유를 클라가 안 듣고 있었다 |
| **파라미터 검사 ≠ 재생 검증** | 값과 결과 사이의 층을 테스트가 건너뛰면 안 된다 |
