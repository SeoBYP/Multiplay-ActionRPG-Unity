# 챕터 29 학습 로그 — 멀티플레이 동기화: 안 보이는 것은 왜 안 보이는가

> 이 트랙은 "던전에서 서로의 애니메이션이 동기화되게 해줘"로 시작해서, **동기화 코드가 아니라 그 앞뒤에서** 네 번 막혔다.
> 네 번 다 증상은 "화면에 안 나온다"였는데 원인은 전부 다른 층에 있었다 — 프리팹 배선, 전투 권위, 세션 수명, 애니메이터 전이.
>
> 공통점은 하나다. **전부 에러가 없었다.** 예외도, 경고도, 실패한 테스트도 없이 조용히 아무 일도 안 일어났다.
> 챕터 27에서 "조용한 실패"를 정리했는데, 이번엔 그 목록에 **"보내지 않은 이벤트"** 와 **"소비되지 않은 파라미터"** 가 추가됐다.
>
> 요약하면: **동기화는 보내는 쪽 코드가 아니라, 받는 쪽에서 그 값이 실제로 소비되는지까지가 기능이다.**

---

## 1. 무엇을 보내고 무엇을 역산할 것인가 — 패킷 설계의 첫 질문

원격 플레이어가 옆걸음을 쳐도 다른 사람 화면에선 전부 전진으로 보였다. 원격이 8방향 블렌드(`Strafe`)를 안 쓰고
1D 트리만 돌리고 있었기 때문이다.

"방향을 패킷에 넣자"가 첫 생각이었는데, 넣기 전에 **이미 보내고 있는 것**을 먼저 셌다.

```
이미 흐르는 것:  위치(PosX/Y/Z) → 시간 미분 → 속도
                회전(RotY)     → facing
        조합 →  로컬 GroundState 와 같은 공식으로 MoveX/MoveY 복원 ⇒ 추가 바이트 0
```

반면 점프·낙하·사다리는 **전부 "y 가 변한다"** 로 같아 위치만으로는 절대 구분되지 않는다. 그래서 그것만 실었다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 8방향 | 안 보냄(역산) | 위치+회전에 이미 들어 있다 |
| 로코모션 모드 | `byte AnimState` 추가 | 역산이 원리적으로 불가능 |
| 회피 방향 | 이동 스트림이 아니라 **회피 이벤트**에 | 1회성 신호를 상시 스트림에 실을 이유가 없다 |

`C_Move` 는 최고빈도 패킷이라 여기 붙는 1바이트는 계속 비용이 된다. **"역산 가능한가"를 먼저 묻는 것**이
패킷 계약을 늘리기 전의 기본 질문이 됐다.

부수적으로 **서버에는 이 값의 enum 을 두지 않았다.** 연출은 클라 권위라 서버는 불투명 byte 로 릴레이만 한다 —
서버가 상태를 해석하기 시작하면 클라 FSM 과 진실원이 둘이 된다. 서버가 모르는 값(200)이 와도 그대로 흘려보내는 것을
테스트로 고정했다.

## 2. 첫 번째 조용한 실패 — 파라미터명이 비어 있었다

구현을 끝내고 테스트를 돌리니 3건이 실패했다. 원인은 내 코드가 아니라 **프리팹**이었다.

```
RemotePlayerCharacter.prefab
  m_animationMoveXFloat:  ''   ← 비어 있음
  m_animationMoveYFloat:  ''
  m_animationStrafeBool:  ''
  m_animationJumpTrigger: ''   ...총 6개
```

`CharacterAgentAnimations` 는 파라미터명이 비면 `SetFloat/SetTrigger` 를 **조용히 스킵**한다. 예외도 경고도 없다.
원격은 원래 `Speed` 하나만 썼고 그건 배선돼 있었으니, 나머지가 비어 있어도 **아무 증상이 없었다.**

여기서 배운 건 기법이 아니라 순서다. **테스트를 먼저 썼기 때문에** 구현 직후에 잡혔다. 나중에 썼다면
"내 구현이 틀렸나"를 한참 들여다봤을 것이다.

## 3. 두 번째 — 죽는 애니가 남에게 안 보였다. 그런데 원인은 전투 권위였다

사망 연출이 자기 화면에서만 나왔다. 처음 세운 가설은 "내가 방금 켠 Jump/Fall/Land 트리거가 Dead 포즈를 밀어냈다"였다.
**회귀 테스트를 3건 먼저 짜서 확인했더니 전부 통과** — 가설이 틀렸다.

그래서 로그를 셌다.

```
양쪽 클라 로그(가상 플레이어 포함)   S_PlayerDead 수신 = 0건 (전 세션)
서버 로그  몬스터 → user 1 공격      = 7회
클라 로그  로컬 HP 피해 적용          = 14회      ← 정확히 2배
```

차액의 정체는 **아군 오사**였다. 피해 수치도 갈렸다 — 몬스터는 `-16/-18`(스탯 산식), 정체불명은 `-10/-15`
(어빌리티 BaseDamage 플랫값). 그리고 그 경로는 이렇게 생겼다:

```
플레이어 A 공격 → 사거리 안 아군 B 선택
   ├─▶ Broadcast S_ApplyEffect{Target=B, -10}  → 클라 B: HP 깎임 ✅
   └─▶ (room.ApplyPlayerEffect 없음)           → 서버 B.Hp: 그대로 ❌

⇒ 클라가 먼저 0 → 로컬 사망 애니만 재생
⇒ 서버는 살아있다고 봄 → S_PlayerDead 영영 미발행 → 원격은 계속 서 있음
```

코드 주석이 원인을 그대로 적어두고 있었다 — `// 플레이어 HP 권위는 클라(결정론 lite) — 서버가 모른다`.
HP 를 서버 권위로 승격할 때 **몬스터→플레이어 경로만** 옮겨졌고 플레이어→플레이어는 옛 방식으로 남은 것이다.
평소엔 아군 오사가 눈에 안 띄어 드러나지 않다가, 둘이 붙어서 콤보를 돌리자 갈라졌다.

> 교훈: **권위를 옮길 때는 "그 값을 바꾸는 모든 경로"를 세어야 한다.** 하나만 남아도 두 값은 반드시 갈라지고,
> 갈라진 뒤엔 그 값에 걸린 모든 판정(사망·다운·부활·던전실패)이 조용히 멈춘다.

해결은 Co-op 이라는 게임 규칙에서 나왔다 — **아군 오사 제거**. "클라만 깎는 HP" 경로 자체가 사라져
두 값이 구조적으로 갈라질 수 없게 됐다. (PvP 를 넣는다면 반드시 서버 차감을 동반해야 한다는 경고를 코드에 남겼다.)

## 4. 세 번째 — 재입장이 30번 거절됐다. 유예가 자기 자리를 막는 줄 알았다

던전 플레이 중 Play 를 껐다 켜면 `방 입장 실패 (시도 N/30)` 가 30줄 쌓였다. 서버 로그에 사유가 있었다:
`Room 3427 is full`.

여기서 한 번 **틀린 설명을 먼저 내놨다.** "재접속 유예(60s)가 슬롯을 물고 있다"고 했는데, 시각을 맞춰보니 아니었다.

```
15:39:34  마지막 패킷 수신
15:39:35  Play 정지 — 소켓이 FIN 없이 사라짐
15:39:40  재입장 시도 → "Room is full" × 30
15:40:37  서버가 유휴 타임아웃으로 죽음 감지   ← 63초 걸림
15:41:37  그제서야 재접속 유예 만료
```

슬롯을 막은 건 유예 장부가 아니라 **아직 죽은 줄 모르는 세션**이었다. 유예는 그 뒤에야 시작된다.
원인을 잘못 짚었으면 "유예 중 세션을 정원에서 빼기"를 고쳤을 텐데, 그건 이 케이스를 전혀 못 고친다.

실제 해결은 **재접속 인수(takeover)** 다 — 같은 UserId 가 들어오면 옛 세션을 비우고 자리를 넘겨받는다.
감지 전이든 유예 중이든 둘 다 덮인다. 비울 때 `graceful:true` 를 쓰는 게 핵심이다: **세션만** 교체하고
PlayerState(위치·HP)는 보존해야 원래 자리로 복귀한다.

같이 고친 두 가지가 더 있다:

- **거절 사유를 클라가 버리고 있었다.** 서버는 `S_PlayerJoined.Message` 에 사유를 담아 보내는데 클라는 `Success` 만 보고
  버렸다. 그래서 콘솔엔 `state=Failed` 30줄만 남고 원인을 알 수 없었다. **진단 정보를 버리는 것도 결함**이다.
- **재시도 예산이 서버 유예보다 짧았다**(30s vs 60s). 기다리는 쪽이 먼저 포기하면 기다리는 의미가 없다.

사유 분기에서 한 가지 판단: **모르는 사유는 재시도**가 기본값이다. 서버 문구가 바뀌었을 때 조용히 포기하는 쪽이
헛돌기보다 나쁘다.

## 5. 네 번째 — 내가 고친 것이 다음 것을 부쉈다

세 번째를 고치는 과정에서 "블렌드 중 AnyState 트리거가 삼켜진다"는 것을 발견하고 `interruptionSource` 로 풀었다.
그러자 **걷기·달리기가 아예 안 나왔다.**

```
frame  0: cur=Locomotion →StrafeLocomotion inTransition=True normTime=0.02
frame 39: cur=Locomotion →StrafeLocomotion inTransition=True normTime=0.03   ← 0.67초 뒤에도 그대로
```

Unity 는 인터럽트가 켜진 전이의 **소스 상태 전이를 다시 평가**한다. 조건(`Strafe=true`)이 계속 참이니
같은 전이가 매 프레임 자기 자신으로 재시작한다 — 8방향 트리에 영영 도달하지 못한다.

해결은 인터럽트가 아니라 **전이 창 자체를 없애는 것**(`duration 0`)이었다. 창이 없으면 트리거가 삼켜질 구간도 없다.
`Strafe` 는 스폰 직후 한 번 켜지고 유지되므로 즉시 전환이 시각적으로도 안전하다.

> 교훈: 프레임워크의 "옵션 하나로 푸는" 해법을 쓸 때는 그 옵션의 **재평가 규칙**까지 알아야 한다.
> 모르면 창을 없애는 쪽이 안전하다 — 없는 창은 어떤 규칙으로도 재평가되지 않는다.

## 6. 왜 213개 테스트가 이걸 전부 통과시켰나

가장 뼈아픈 부분이다. Walk/Run 이 안 나오는 상태에서 **PlayMode 213개가 전부 초록**이었다.

이유는 단순하다. 애니 테스트가 전부 **파라미터 값**만 봤다:

```
❌ Assert.Greater(animator.GetFloat("MoveX"), 0.5f)      // 값은 들어갔다
✅ Assert.IsTrue(info.IsName("StrafeLocomotion"))         // 그 값을 소비해 상태에 도달했나
✅ Assert.Greater(after.normalizedTime, before)           // 그 상태에서 시간이 흐르나
```

"값을 넣었다"와 "그 값이 재생으로 이어졌다" 사이에 상태 머신이라는 층이 통째로 빠져 있었다.
새 테스트는 그 층을 본다.

그리고 **그 테스트가 정말 이 버그를 잡는지 실측**했다 — 컨트롤러에 고장을 주입해 2/2 실패를 확인하고 복구했다.
챕터 27에서 배운 것("테스트를 추가했다 ≠ 그 테스트가 이 버그를 잡는다")을 이번엔 처음부터 적용했다.

부수적으로 하네스 함정도 다시 밟았다. 처음엔 캐릭터 프리팹을 통째로 Instantiate 했더니 DI 없는 컴포넌트가
NRE 를 던졌고, **그 로그가 테스트를 실패시켜 진짜 신호를 덮었다.** 컨트롤러만 단독으로 굴리도록 좁혀서 해결했다.
통합 범위를 넓게 잡으면 무관한 실패가 신호를 먹는다 — 챕터 27과 같은 결론에 다른 경로로 도착했다.

## 처음 생각한 것 → 피드백/데이터로 수정된 것

| 처음 | 실제 |
|---|---|
| "방향을 패킷에 넣어야 한다" | 위치+회전에 **이미 들어 있다**. 넣을 것은 역산 불가능한 **모드 1바이트**뿐 |
| "서버도 상태 enum 을 알아야 한다" | 연출은 클라 권위 — 서버가 해석하면 **진실원이 둘**이 된다. 불투명 byte 릴레이 |
| "사망 연출이 안 나오는 건 연출 코드 문제" | 연출은 멀쩡했다. **서버가 죽은 걸 몰랐다**(아군 오사가 클라 HP만 깎음) |
| "내가 켠 트리거가 Dead 를 밀어냈다" | 회귀 테스트 3건 먼저 짜서 확인 → **가설 기각**. 그 다음에 로그를 셌다 |
| "재접속 유예가 슬롯을 막는다" | 아니었다. **아직 죽은 줄 모르는 세션**이 막았다(감지에 63초). 원인을 잘못 짚었으면 엉뚱한 걸 고칠 뻔했다 |
| "블렌드 중 트리거 유실은 interruptionSource 로 푼다" | 전이가 **자기 자신으로 재시작**해 Walk/Run 이 통째로 사라졌다. 창을 없애는 게 답 |
| "테스트 213개가 초록이면 안전하다" | 전부 **파라미터만** 봤다. 상태 도달·재생 진행은 아무도 안 봤다 |

## 핵심 키워드

역산 가능성으로 패킷 설계(보낼 것 vs 이미 흐르는 것) · 연출=클라 권위, 서버는 불투명 릴레이 ·
파라미터명 미배선의 조용한 스킵 · **권위 이전 시 "그 값을 바꾸는 모든 경로" 세기** · 클라·서버 HP 발산이 삼킨 사망 이벤트 ·
가설을 테스트로 먼저 기각하기 · 로그 개수 세기(7 vs 14)로 원인 좁히기 · 잘못 짚은 원인을 데이터로 정정 ·
FIN 없는 끊김과 유휴 타임아웃(63초) · 재접속 인수(세션만 교체, 상태 보존) · 진단 정보를 버리는 것도 결함 ·
모르는 실패는 재시도가 안전 기본값 · 인터럽트 전이의 자기 재시작 · **파라미터 검사 ≠ 재생 검증** ·
회귀 포착 실측(고장 주입) · 통합 범위를 좁혀 무관한 실패 배제
