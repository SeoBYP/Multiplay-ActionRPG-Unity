# 24. Co-op 부활 — 로그조차 안 찍히던 버그의 원인은 한 줄이었다

> **한 줄** — 부활 자체는 기존 골격(클라 입력 → 서버 검증 → 브로드캐스트)의 재사용이라 **새 패킷 2개**로 끝났다. 정작 시간을 잡아먹은 건 **의존성을 잘못된 방법으로 가져온 한 줄**이었고, 그 회귀를 잡은 건 단위 테스트가 아니라 **전체 PlayMode 스위트**였다.
>
> **범위** 서버 권위 재사용 · 원자적 멱등 검증 · 과거 결정 뒤집기 · DI vs 컴포넌트
> **의미** 포트폴리오가 약속한 **Co-op**의 마지막 조각

---

## 1. 새로 만든 것이 거의 없다

```
아군 다운 (State.Dead / HP 0)                        ← 기존
   → 시전자가 사거리 안에서 E → C_Revive{TargetUserId}    (신규 패킷 1824)
   → 서버 Room.TryRevive 검증
        → HP = MaxHp × 50% + 다운 목록에서 제거
   → S_PlayerRevived{UserId, Hp} 방 브로드캐스트          (신규 패킷 1825)
```

HP([21](./chapter-21-connection-liveness-hp-authority.md))·마나·회피([23](./chapter-23-mana-resource-authority-ability.md))에서 쓴 **"클라 입력 → 서버 권위 검증 → 브로드캐스트"** 틀을 그대로 얹었다. 패킷 ID도 던전 이벤트 대역(1800~1899)에 자연스럽게 들어간다.

**골격이 자리를 잡으면 새 메커닉의 비용이 급격히 떨어진다.** 이 챕터에서 새로 고민한 것은 "무엇을 검증할까"뿐이었다.

## 2. 검증을 한 메서드에 모으고, 멱등으로 만든다

```csharp
// Room.cs:461
public (bool Ok, int NewHp) TryRevive(long reviverId, long targetId)
```

검증 순서가 곧 설계다.

```
① 자기 자신인가                        → 거부
② 던전이 이미 실패 확정인가            → 거부   (_outcome == Failed)
③ 시전자가 입장·생존 상태인가          → 거부
④ 대상이 존재하는가                    → 거부
⑤ 사거리 안인가 (ReviveConfig)         → 거부
⑥ _downed.Remove(targetId) 가 성공?    → 실패면 거부   ← 여기가 멱등의 핵심
```

**⑥이 원자적 멱등 지점**이다. 중복 `C_Revive`가 와도 두 번째는 `Remove`가 `false`를 반환해 거부된다 — **두 번 살아나거나 HP가 두 번 차는 일이 없다.**

②는 **재사용**이다. `_outcome`은 [14](./chapter-14-dungeon-clear-loop.md)에서 클리어/실패를 배타적으로 만들려고 도입한 값인데, "실패 확정 후에는 부활 불가"라는 새 규칙이 **그 값 하나를 읽는 것으로** 표현된다.

> **상태를 한 곳에 모아 두면 나중에 붙는 규칙도 그 하나만 본다.** 만약 클리어/실패가 별도 bool 두 개였다면 여기서 둘 다 검사해야 했고, 새 규칙이 생길 때마다 검사 목록이 늘었을 것이다.

같은 패턴을 계속 쓰고 있다 — `TryBeginDodge`([23](./chapter-23-mana-resource-authority-ability.md) 2절), `SET NX PX`([16](./chapter-16-main-loot-path.md) 4절), `CompareExchange`([14](./chapter-14-dungeon-clear-loop.md) 1절). **검증과 상태 변경을 하나로 묶는 것.**

## 3. 권위 경계 — 무엇까지 서버가 볼 것인가

```
서버가 본다   거리 · 다운 상태 · 시전자 생존      ← 게임 결과를 바꾸는 불변식
클라가 한다   홀드 UX · 프롬프트 표시             ← 결과를 바꾸지 않는 연출
```

부활은 데미지 익스플로잇이 아니다. 위조해도 **아군이 살아날 뿐**이라 위험도가 낮다. 그래서 거리와 상태만 서버가 확인하면 충분하다.

> **권위를 어디까지 가져올지는 "위조했을 때 무엇을 얻는가"로 정한다.** 전부 서버로 올리면 안전하지만 반응성과 복잡도를 지불한다([authority-model](../wiki/authority-model.md)의 4축 판단).

## 4. 한 기능이 과거의 결정을 뒤집었다

이전 작업에서 **원격 플레이어가 다운되면 그 캐릭터를 Destroy**했다. 당시 목적은 "다운을 남에게 보이게 하는 것"이었고, 다운 포즈는 후속이라 그냥 지웠다.

부활을 붙이려니 이 결정이 정면으로 막았다 — **살리려면 다운된 아군이 상호작용 대상으로 씬에 남아 있어야 한다.** 지워버리면 다가가도 아무것도 없다.

```
이전:  S_PlayerDead{원격} → Destroy                       ← 부활 불가능
이후:  S_PlayerDead{원격} → DownedAllyMarker 부착(보존)   → 부활 대상
       S_PlayerRevived{원격} → 마커 제거(정상 복귀)
```

> **"지금 안 쓰니까 간단히 지운다"는 결정은, 나중 기능이 그 흔적을 필요로 할 때 빚이 된다.**
>
> 다만 **그때 미리 만들지 않은 건 옳았다**(YAGNI). 핵심은 그 결정을 **국소화**해 둔 것이다 — 분기 하나였기 때문에 한 줄로 되돌릴 수 있었다. 여러 곳에 흩어져 있었다면 같은 되돌리기가 훨씬 비쌌다.

## 5. "아예 안 되던" 진짜 원인 — 로그조차 안 찍혔다

코드도, 단위 테스트도, E2E도 전부 그린이었다. MPPM으로 두 창을 켜서 실제로 해 보니 **부활이 전혀 동작하지 않았다. 로그가 한 줄도 안 떴다.**

로그가 없다는 게 단서였다 — 판정 실패라면 거부 로그라도 떴을 것이다. **코드가 그 지점에 도달조차 못 하고 있었다.**

원인은 한 줄이었다.

```csharp
// 내가 쓴 코드 — 항상 null 을 반환한다
var input = _container.TryResolve(typeof(ICharacterInputSource), out var i) ? ... : null;
```

`ICharacterInputSource`를 **DI 컨테이너에서** 가져오려 했는데, 이 프로젝트에서 입력은 **DI 등록이 아니라 플레이어 GameObject에 붙은 컴포넌트**(`CharacterInputBuffer`)다. 원래 소비자는 이렇게 가져오고 있었다.

```csharp
// CharacterAgent — 원래 있던 방식
InputSource = GetComponent<ICharacterInputSource>();
```

`TryResolve`는 항상 null을 돌려줬고, `ReviveInteractor.Update`는 첫 줄 `if (_input == null) return;`에서 매 프레임 빠져나갔다. **null 가드가 실패를 침묵으로 바꾼 것**이다.

고친 건 한 줄이다.

> **의존성을 소비하기 전에 그것이 어떻게 제공되는지**(DI 등록 / 씬 컴포넌트 / 수동 주입)를 먼저 확인해야 한다. 가장 안전한 방법은 **이미 같은 것을 쓰는 소비자를 그대로 따라 하는 것**이다. 에이전트가 `GetComponent`로 가져오면 나도 `GetComponent`다. "당연히 DI에 있겠지"가 화근이었다.

### 학습을 코드에 남겼다

지금 `ReviveInteractor`에는 두 가지가 박혀 있다.

```csharp
// :15  doc comment — "…에서 GetComponent — 에이전트와 동일(DI 아님)"
// :35  Debug.Log($"[ReviveInteractor] 활성화 — 입력={(_input != null ? "OK" : "없음")} …")
```

주석은 **왜 이 방식인지**를 남기고, 진단 로그는 **같은 실패가 다시 나면 즉시 보이게** 만든다. 원래 이 로그가 있었다면 "로그조차 안 뜬다"에서 헤맬 이유가 없었다.

## 6. 그 회귀를 잡은 건 전체 스위트였다

입력 버그와 **별개로**, 처음 짠 코드는 단위 테스트와 컴파일을 전부 통과했다. 그런데 "실 테스트 전에 E2E·PlayMode를 *전부* 통과시키라"는 지시에 따라 전체를 돌리자 2건이 빨갛게 떴다.

```
CharacterSpawnMultiClientTests
VContainerException: No such registration of type: ICharacterInputSource
```

`ReviveInteractor`를 `[Inject]`로 만들었는데, **스폰 전용 테스트 스코프에는 입력이 등록돼 있지 않아** `_container.Inject`가 throw했다.

**부활과 아무 상관 없는 스폰 테스트가 깨졌다.** 단위·컴파일·부활 E2E만 봤다면 절대 못 봤을 자리다. (이후 `GetComponent` 전환으로 DI 의존 자체가 사라져 근본 해소됐다.)

> **"플레이 검증은 사용자 영역"으로 넘기기 전에, E2E + PlayMode 전체를 먼저 그린으로 만든다.** 단위만 보면 인접 기능의 회귀가 조용히 샌다. 느린 생존성 테스트(70~80초)가 섞여 있어도 전체를 돌린다 — **사람이 켜서 발견하는 것보다 싸다.**
>
> 같은 교훈을 [17](./chapter-17-equipment-system.md) 8절에서도 얻었다. 그때는 생성자에 의존성을 추가해 DI 호스트 4곳이 깨졌다. **DI는 컴파일러가 검사해 주지 않는 배선**이라, 조립 지점을 실제로 실행해 보는 테스트만이 검증할 수 있다.

## 7. 코어가 먼저, UX는 그다음

처음엔 부활에 **홀드(길게 누르기)** 채널을 정교하게 설계했다. 그런데 코어가 동작하지 않는 상태에서 홀드 로직을 다듬는 건 순서가 틀렸다 — 요청에 따라 **사거리 + E 즉시**로 단순화했다.

**코어가 먼저 동작해야 그 위에 얹을 UX의 모양이 보인다.** 홀드는 폴리시이고, 폴리시는 검증 가능한 코어 다음이다.

## 이 챕터에서 뒤집힌 생각

| 처음 생각 | 실제 |
|---|---|
| "입력은 DI에 있겠지" | **씬 컴포넌트**였다. `TryResolve`는 항상 null → 로그조차 0줄 |
| "단위+컴파일 그린이면 플레이는 사용자가" | **전체 PlayMode**가 인접 스폰 테스트의 DI 회귀를 잡았다 |
| "홀드 채널부터 정교하게" | 코어(사거리+E)가 먼저 동작해야 한다 |
| "원격 다운은 지우면 되지" | 부활이 그 결정을 뒤집었다. 국소화해 둬서 한 줄로 되돌림 |
