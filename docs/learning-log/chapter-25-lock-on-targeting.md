# 챕터 25 학습 로그 — 타겟팅/락온: "패킷 0"의 근거 · 두 축 분리 · Unity의 가짜 null

> 락온(타겟 고정)은 보통 "카메라 + 조준"을 한꺼번에 건드리는 큰 작업처럼 보인다.
> 그런데 이 프로젝트에선 **새 패킷도, 서버 코드도 0줄**로 끝났다 — 그게 이 챕터의 핵심이다.
> ① 기능을 어느 레이어가 소유하는지 먼저 따지면 "건드릴 것"이 극적으로 줄어든다(락온 = 클라 조준 보조).
> ② 이동과 바라보기(facing)는 **다른 축**이다 — 분리해 두면 "이동은 카메라기준, 몸은 타겟" 같은 조합이 공짜로 나온다.
> ③ Unity의 `== null`은 **거짓말을 한다**(파괴된 객체를 null인 척). 그 함정이 "죽은 적에 카메라가 영원히 잠기는" 버그를 만들었고, 테스트가 잡았다.

---

## 1. "패킷 0"의 근거 — 락온은 누가 소유하는가

처음 떠오른 그림은 "락온 상태를 서버에 보내고, 서버가 조준을 고정한다"였다. 하지만 한 단계 앞서 물었다 — **락온은 게임 결과(데미지·적중)를 바꾸는가, 아니면 조준/연출인가?**

답: 조준 보조다. 적중 판정은 이미 **플레이어의 facing/위치**로 결정된다(던전=서버 hitbox, Main=`LocalCombat`). 그리고 그 facing은 던전에서 `MoveSyncSender`가 **정지 중에도** rotY를 서버로 보낸다. 그러면 결론이 따라온다:

```
락온이 해야 할 일 = 플레이어를 타겟 쪽으로 "회전"시키는 것, 그게 전부다.
   회전 → rotY 변함 → C_Move 송신(기존) → 서버 hitbox 자동 정렬   (던전)
   회전 → 같은 facing 으로 LocalCombat 판정                         (Main)
→ 새 패킷·서버 게이트 불필요.
```

> 교훈: "이 기능을 네트워크로 보내야 하나?"의 답은 대개 **"그 기능이 권위를 가지나?"**에 달려 있다. 락온은 권위가 없다(조준은 클라의 자유). 권위 있는 facing은 *이미* 동기화되고 있었으니, 락온은 그 위에 올라타기만 하면 됐다. 레이어 소유권을 먼저 따진 덕에 작업이 "클라 5파일 + 마커"로 줄었다.

## 2. 두 축 분리 — 이동(카메라기준)과 facing(타겟)은 별개다

소울류 락온의 손맛은 **"몸은 적을 보면서, 이동은 좌우로 스트레이프"**다. 이게 가능했던 건 모터가 이미 **이동 방향**과 **바라보는 방향**을 따로 계산하고 있었기 때문이다.

```
CharacterMotor.Move(input)
   ├─ DesiredMoveDirection  = 회전전략(카메라기준)   ← 락온이 안 건드림 = 스트레이프 유지
   └─ DesiredFacingDirection = 회전전략(카메라기준)   ← 락온이 여기만 덮어씀(FacingOverride)
```

연결점은 딱 두 개였다:

- `CharacterMotor.FacingOverride`(nullable) — 값이 있으면 회전전략 대신 **타겟 방향**을 바라본다. 이동은 무영향.
- `CharacterCameraFollow.LockTarget`(Transform) — 값이 있으면 마우스 Look 대신 카메라 피벗을 타겟 쪽으로 수렴.

`LockOnDriver`(순수 C#, `DodgeDriver`·`KnockbackDriver`와 같은 형제)가 매 프레임 이 둘에 push한다. **상태머신에 락온 상태를 새로 만들지 않았다** — 락온은 이동 모드(Locomotion)가 아니라 그 위에 직교하는 조준 보조(Action 축)이기 때문이다(CA-1 원칙).

> 교훈: 입력→이동을 "한 덩어리"로 짰다면 락온은 침습적 수술이 됐을 것이다. **이동과 facing을 애초에 분리**해 둔 덕에, 한쪽(facing)만 nullable 오버라이드로 가로채는 한 줄짜리 변경이 됐다.

두 종류의 몬스터(던전 `MonsterEntity` = 서버 보간, Main `LocalMonster` = 클라 권위)는 클래스가 다르지만, **`LockOnTarget` 마커 하나**(정적 레지스트리, 부활의 `DownedAllyMarker`와 같은 패턴)를 양쪽 프리팹에 붙여 통일했다. 드라이버는 물리 레이어를 모른 채 "화면 중앙에 가장 가까운 마커"를 고른다(`WorldToViewportPoint`).

## 3. Unity의 가짜 null — "죽은 적에 카메라가 영원히 잠긴다"

코드가 다 돌아가는 듯했지만, 테스트 하나가 빨갛게 떴다 — `대상_소실시_자동_언락된다`. 원인은 한 줄이었다:

```csharp
public void Tick()
{
    if (_target == null) return;   // ← 함정
    if (!IsTargetValid()) { ForceUnlock(); ... }
    ...
}
```

Unity의 `==`는 **파괴된 오브젝트를 null인 척** 돌려준다(C#의 진짜 null이 아닌데도). 그래서 락온한 몬스터가 죽으면 `_target == null`이 **true**가 되어 첫 줄에서 그냥 `return` — `ForceUnlock()`을 **건너뛴다.** 결과: 카메라의 `LockTarget`과 모터의 `FacingOverride`가 풀리지 않고, **카메라가 죽어 사라진 적의 자리에 영원히 잠긴다.**

고친 방법은 "미락(진짜 null)"과 "락 중인데 대상이 파괴됨(가짜 null)"을 구분하는 것:

```csharp
if (ReferenceEquals(_target, null)) return;   // 진짜 C# null = 애초에 락 안 함 → 아무것도 안 함
// 가짜 null(파괴됨)은 여기로 내려와 IsTargetValid()=false → ForceUnlock() 으로 정리
```

`ReferenceEquals`는 Unity의 연산자 오버로드를 우회해 **관리 참조 자체**를 본다. 락 중 파괴된 대상은 (가짜 null일 뿐) 관리 참조는 살아 있으므로 `ReferenceEquals`는 false → 유효성 검사로 내려가 정리된다.

> 교훈: Unity에서 `obj == null`은 **두 가지 다른 상태**(진짜 미할당 / 파괴됨)를 같은 답으로 뭉갠다. 그 둘을 다르게 처리해야 하는 코드(여기선 "락 안 함" vs "락 중 대상 소실")에선 `ReferenceEquals`로 진짜 null만 따로 봐야 한다. 이건 클라 게임플레이 곳곳에 숨은 함정이다.

그리고 이 버그를 잡은 건 **사람이 아니라 테스트**였다. `대상_소실시_자동_언락된다`는 정확히 "락 → 타겟 Destroy → Tick → 풀렸는가"를 단언한다. 손으로 플레이하며 "어, 카메라가 이상한데?"로 발견했다면 원인까지 한참 걸렸을 것을, 테스트가 즉시 짚었다.

## 처음 생각한 것 → 피드백으로 수정된 것

- **"락온 상태를 서버에 보내야지"** → 아니다. 락온은 권위가 없는 조준 보조. 권위 있는 facing은 이미 동기화 중 → **패킷 0**. 레이어 소유권을 먼저 따진 결과다.
- **"락온 = 새 Locomotion 상태"** → 아니다. 이동 모드가 아니라 그 위에 직교하는 Action 축. FSM 상태를 만들지 않고 `FacingOverride` 한 곳만 가로챔.
- **"키는 E로"(사용자 최초)** → E는 Interact(부활·줍기·대화)와 충돌. 한 번 누르면 둘 다 터진다 → 충돌 없는 **Tab**으로 확정. *기존 바인딩을 먼저 확인*하는 게 키 추가의 1단계.
- **"`obj == null`이면 안전하지"** → Unity에선 파괴된 객체도 null인 척한다. "락 안 함"과 "락 중 소실"을 뭉개 카메라가 영구 잠겼다 → `ReferenceEquals`로 분리.

## 핵심 키워드

- **레이어 소유권 → 네트워크 비용**: "권위가 없는 기능(조준)"은 클라에서 끝난다. 이미 동기화된 facing에 올라타 패킷 0.
- **이동/​facing 축 분리**: 둘을 따로 계산해 두면 "이동은 카메라기준, 몸은 타겟"이 nullable 오버라이드 한 줄로 나온다.
- **레지스트리 마커 재사용**: 무관한 두 클래스(서버/클라 몬스터)를 마커 컴포넌트 하나로 통일(물리 레이어 무의존). 부활의 `DownedAllyMarker`와 같은 틀.
- **Unity의 가짜 null**: `== null`은 미할당과 파괴를 같은 답으로 뭉갠다. 구분이 필요하면 `ReferenceEquals`.
- **테스트가 잡는 정리 버그**: "대상 소실 시 자동 해제"를 단언한 테스트가 손플레이보다 먼저, 정확히 원인을 짚었다.
