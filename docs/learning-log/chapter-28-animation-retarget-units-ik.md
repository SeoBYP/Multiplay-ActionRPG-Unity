# 챕터 28 학습 로그 — 애니메이션은 계약이다: 아바타·단위·좌표계, 그리고 IK는 덮어쓰기가 아니다

> 이 트랙은 "ARPGWarrior 애니 팩을 붙이자"로 시작했다. 붙이는 작업은 하루면 끝날 줄 알았는데,
> **컨트롤러에 클립 22개가 정상 배선된 상태에서 캐릭터가 지면에 파묻혀 있었다.**
>
> 이번에 반복해서 걸린 것은 전부 같은 종류였다. **어떤 계약 위에서 말하고 있는지를 명시하지 않은 값들.**
> 아바타 타입(Generic ↔ Humanoid), 블렌드 파라미터의 **단위**, 사다리의 **좌표계**, IK의 **의미**.
> 넷 다 "들어가긴 하는데 뜻이 다른" 값이라 컴파일도, 테스트도, 로그도 아무 말을 하지 않았다.
>
> 요약하면: **타입이 맞는다고 계약이 맞는 건 아니다. 애니메이션에서 그 불일치는 예외가 아니라 어색함으로 나타난다.**

---

## 1. 배선은 완료였는데 아무것도 안 붙었다 — 아바타 타입이라는 계약

기존 `PlayerController.controller`는 상태·전이·파라미터가 다 맞았다. 클립도 22개 전부 지정돼 있었다.
그런데 플레이어 메시가 `SK_HornedKnight_M_02`(**Humanoid**)로 교체돼 있었고, 그 클립들은 전부 **Generic**이었다.

Generic 클립은 **본 이름으로 직접** 바인딩되고, Humanoid 클립은 **머슬 공간**을 거쳐 리타깃된다.
둘을 섞으면 Unity는 에러를 내지 않는다. 그냥 **아무 본도 움직이지 않는다.**

```
[측정] 재생 중 본 회전량
   구 클립(Generic) → Humanoid 아바타 :  0.0도      ← 배선은 완료, 결과는 정지
   ARPG 클립(Humanoid) → 같은 아바타  : 15.5도      ← 정상 리타깃
```

더 나쁜 건 정지가 아니라 **빈 휴머노이드 포즈**였다. 클립이 아무것도 안 쓰니 아바타 기본 포즈가 적용되면서
`root` 본이 −1.06m로 내려가 캐릭터가 지면에 박혔다. 화면상 증상("파묻혔다")과 원인("리타깃 실패")이
전혀 닮지 않아서, 스크린샷만 보면 콜라이더나 스폰 높이를 의심하게 된다.

**그래서 첫 판단을 실측으로 했다.** 컨트롤러를 고치기 전에 "이 조합에서 본이 움직이는가"를 각도로 재고,
0.0도를 확인한 뒤에야 방향을 정했다(구 컨트롤러 유지 → 폐기, ARPG 기반 신규 생성).

> 교훈: 애니메이션에서 "배선 완료"는 아무것도 보장하지 않는다. **재생 중 본이 실제로 움직이는가**가 최소 확인선이다.

## 2. 컨트롤러를 손이 아니라 코드로 만든 이유

새 컨트롤러는 상태 15개 · 파라미터 19개 · 18모션 블렌드 트리다. 이 규모를 에디터에서 손으로 만들면
**diff가 남지 않고 재현이 안 된다.** 실제로 구 컨트롤러가 모델 교체 때 조용히 깨진 게 그 결과였다 — 언제 무엇이
어긋났는지 추적할 방법이 없었다.

그래서 `PlayerAnimatorControllerBuilder`(Editor)로 **전량 코드 생성**하고, 매번 `DeleteAsset` 후 처음부터 만든다.
부분 갱신은 잔여 상태가 남아 "내 머신에서만 되는" 컨트롤러를 만든다.

부수적으로 이게 **계약을 테스트 가능하게** 만들었다. `PlayerAnimatorContractTests`가 생성물을 직접 열어
"루트모션 태그는 공격 상태에만 붙는가", "블렌드 좌표가 정규화가 아니라 m/s인가"를 단언한다.

## 3. 발 슬라이딩은 버그가 아니라 단위 불일치였다

발이 미끄러지는 걸 처음엔 "블렌드가 덜 됐나" 정도로 봤다. 실제 원인은 훨씬 단순했다 — **파라미터의 단위**.

블렌드 트리 좌표를 "코드가 원하는 속도"(Walk 2.0 / Run 4.0)로 저작해 뒀는데, 클립의 실제 이동 속도는
2.26 / 3.31이었다. 2.0을 넣으면 2.26짜리 클립이 나오고, 몸은 2.0으로 간다. **13% 헛돈다.**

```
[예전] 좌표계 = "내가 정한 속도"        [지금] 좌표계 = 클립 실측 속도(m/s)
  파라미터 2.0 ─▶ 클립 2.26 재생          파라미터 2.26 ─▶ 클립 2.26 재생
  몸        2.0                            몸           2.26
  ⇒ 어긋남                                 ⇒ 발 속도 == 이동 속도 (실측 비율 1.00)
```

고친 방식이 중요하다. **보정 계수를 곱해 증상을 지운 게 아니라, 파라미터의 의미를 "m/s"로 바꿔 문제를 소멸시켰다.**
좌표는 `AnimationClip.averageSpeed`로 **측정**해 상수로 저작한다. 이후로는 이동 속도를 바꿔도 자동으로 맞는다.

Sprint만 예외다. 게임 속도(5.335)가 클립(3.44)보다 빨라 좌표로는 표현할 수 없으니 `timeScale ≈ 1.55`로 배속했다.
**"좌표로 해결되는 것"과 "배속이 필요한 것"의 경계가 클립 속도**라는 게 이 구조의 규칙이다.

### 3-1. 같은 원리, 다른 구현 — 몬스터는 왜 안 되나

몬스터도 미끄러진다길래 같은 기법을 쓰려다 막혔다. 몬스터 보행 클립은 전부 **제자리(in-place)** 라
`averageSpeed`가 0이다. 좌표에 넣을 값 자체가 없다.

세 안을 놓고 골랐다:

| 안 | 내용 | 왜 아닌가 / 왜 맞나 |
|---|---|---|
| A | 클립을 루트모션으로 재저작 | 에셋 원본 수정 — 팩 업데이트 시 소실 |
| B | 이동 속도를 클립에 맞춰 전부 하향 | 게임 밸런스(추격 속도)를 애니가 결정하게 됨 |
| **C** | **배속 보정 + 상한 초과분만 속도 하향** | 대부분은 배속으로 흡수, 극단값만 밸런스 양보 (**채택**) |

배속 상한을 2.0으로 둔 건 그 이상 빨리 돌리면 걷기가 종종걸음으로 보이기 때문이다. 상한을 넘는 몬스터만
이동 속도를 낮춰 맞춘다. **한 원리(발 속도 = 이동 속도)를 두 제약(루트모션 클립 / 제자리 클립)에 맞춰 두 구현으로 낸 셈이다.**

## 4. 자동 측정이 틀린 데이터를 만든다 — "미측정"이 나은 경우

제자리 클립의 속도는 **발 본의 후방 이동 속도**로 잰다. 처음엔 이걸 런타임에 자동 측정하려 했는데,
리그마다 본 이름이 달라 매칭이 빗나갔다. 리바이어던이 **10m/s**로 측정됐다 — 촉수를 발로 잡은 것이다.

여기서 방향을 바꿨다. 자동 측정을 넣으면 **오측정이 그대로 데이터가 되고**, 그 값은 아무 경고 없이
캐릭터를 이상하게 만든다. 그래서 측정은 도구로 한 번만 돌리고 **값은 표에 저작**했다.
그리고 못 잰 몬스터(gargoyle · leviathan)는 추정치를 넣지 않고 **0 = 무보정**으로 뒀다.

> 교훈: 틀린 값은 없는 값보다 나쁘다. 무보정은 "약간 미끄러짐"이지만, 오측정은 "왜 저러는지 모르겠음"이다.

## 5. 타이밍을 애니메이터에 두지 않은 이유

4단 콤보를 만들면서 처음엔 상식대로 **애니메이터 체인 전이 + `hasExitTime`** 을 쓰려 했다.
동작하지 않았다 — 전이 대기 중에 Unity가 `Attack` **트리거를 소실**한다(실측).

우회하려면 트리거 대신 bool을 쓰거나 exit time을 잘게 조정하는 방법이 있는데, 그 방향은
**타이밍의 진실원이 애니메이터로 가는 것**이라 접었다. 데미지 판정과 서버 cadence 검증이
같은 타이밍을 봐야 하는데, 애니메이터 안의 숫자는 서버가 읽을 수 없다.

```
[선택한 구조]
스킬 데이터(SkillTimeline.ComboChainMs / ComboWindowMs)   ← 진실원 하나
   ├─▶ 클라 ComboDriver : 언제 다음 타를 쏠지
   └─▶ 서버 cadence 게이트 : 너무 빠른 입력을 거부

애니메이터 전이는 hasExitTime = false (코드가 쏘는 순간 전이)
   ⇒ 애니 체인 시점 == 데미지 시점 == 서버 검증 기준
```

애니메이터는 "보여주기"만 하고 **"언제"는 데이터가 갖는다.** 결과적으로 애니·데미지·네트워크가 어긋날 여지가 사라졌다.

## 6. 사용자 피드백이 드러낸 설계 구멍 — 선입력의 의미는 단계마다 다르다

콤보에 선입력 버퍼를 넣었다. "다음 타가 나갈 시점 전에 누른 입력을 버리지 않고 담아뒀다가 그 시점에 발동"하는,
액션 게임의 표준 장치다. 여기까지는 잘 돌았다.

그런데 실제로 플레이해 보니 **마지막 타를 치는 도중에 누르면, 애니가 끝나고 Idle이 된 뒤에 한 대가 더 나갔다.**

원인은 버그가 아니라 **의미의 미끄러짐**이었다. 선입력은 "이어지는 다음 타"를 위한 장치인데,
마무리 타 뒤에는 이어질 타가 없다 — 그 입력은 **새 콤보의 첫 타**가 된다. 같은 버퍼인데 뜻이 다르다.

```
1타~3타 중 입력  → "이어서 4타"      = 담아둔다 (의도한 동작)
4타(마무리) 중 입력 → "새 콤보 시작"  = 버린다   (손을 뗐는데 나가면 안 됨)
```

머리로 설계할 때는 두 경우가 같아 보였고, **플레이해 봐야 갈렸다.** 순수 로직이라 테스트로 고정하기는 쉬웠지만,
**그 케이스를 떠올리게 한 건 테스트가 아니라 사용자 피드백**이었다.

## 7. 사다리: 좌표계를 말하지 않으면 세 번 틀린다

사다리 하나에서 방향 문제로 세 번 연속 틀렸다. 셋 다 원인이 같다 — **"어느 좌표계에서 말하고 있는가"를 명시하지 않음.**

| # | 증상 | 무엇을 착각했나 |
|---|---|---|
| 1 | 가까이 가도 아무 반응 없음 | 콜라이더를 **월드 바운드**로 계산 → FBX의 −90° 회전·스케일 100을 무시해 두께 0.06m짜리 납작한 판이 됨 |
| 2 | 옆에서 접근하면 측면 기둥에 옆으로 매달림 | 부착 방향을 **접근한 방향 그대로** 사용(면이라는 개념 없음) |
| 3 | 한쪽 면에서는 좌우가 정확히 반대 | 좌우를 **사다리 고정 축**으로 계산 → 반대편에 서면 캐릭터의 왼쪽이 그 축의 오른쪽 |

3번이 특히 교훈적이다. **정확히 절반만 맞아서** 처음에는 "값이 좀 안 맞네" 정도로 보였다.
부호 하나가 뒤집힌 문제는 한쪽 케이스만 보면 정상으로 보인다.

해결은 전부 **기준을 명시**하는 것이었다. 콜라이더는 로컬 공간에서, 부착은 **면 법선**에 스냅, 좌우는 **캐릭터의 `right`** 기준.
그리고 앞/뒤 양쪽 면에서 값을 실측해 대칭인지 확인했다(오른손 +0.33 / 왼손 −0.33, 양쪽 동일).

부수적으로 `GetFaceAxes()`는 콜라이더의 **월드 두께**로 축을 판별한다 — 얇은 수평축이 면 법선, 넓은 쪽이 폭.
FBX가 어떻게 회전돼 있든 무관하게 동작한다. **에셋 저작 상태에 의존하지 않는 판별식**을 고른 것이다.

## 8. IK는 덮어쓰기가 아니라 보정이다

가장 많이 고쳐 쓴 부분이다. 처음 만든 IK는 이랬다: 사다리에 붙어 있는 동안 **네 팔다리를 전부 기둥·발판 좌표로 지정**.
"정답 위치를 알고 있으니 거기로 보낸다"는 발상이었다.

피드백이 두 번 왔고, 두 번 다 같은 방향을 가리켰다.

**① "항상 IK를 걸 게 아니라 사다리를 잡는 손·발만"**
→ 붙잡은 팔다리는 월드에서 거의 정지해 있고(몸만 올라감), 뻗는 팔다리는 몸보다 빠르게 움직인다.
그 **속도 차**로 팔다리별 가중치를 만들었다. 별도 커브 저작 없이 클립에서 직접 판정한다.

**② "팔 간격이 애니메이션이랑 달라. 간격은 맞추고, 위치만 팔 뻗어서 닿을 때만"**
→ 이게 결정적이었다. 손 위치를 통째로 덮어쓰니 클립이 가진 **어깨너비 간격**이 사라지고
항상 기둥 폭(±0.33)으로 벌어져 있었다. 즉 **고칠 필요가 없는 축까지 고치고 있었다.**

```
클립이 만든 손 위치
   │ 사다리 좌표계로 분해
   ├── 좌우(팔 간격) ──▶ 그대로 둔다     ← 클립이 이미 옳다
   ├── 깊이(면까지)  ──▶ 보정한다        ← 사다리 위치는 클립이 모른다
   └── 높이          ──▶ 발판으로 스냅   ← 발판 간격 0.6m는 클립 제작 기준과 다르다

가중치: |클립 위치 − 목표| < 0.28m 일 때만 (뻗는 중·당기는 중 = 0)
```

②를 반영하면서 판정도 속도비에서 **거리(접촉)** 로 바꿨다. 요구가 "뻗어서 **닿을 때만**"이었으니
거리로 재는 게 요구와 1:1이다. 속도비는 같은 결과를 간접적으로 근사하던 것이었다.

> 교훈: IK의 기본값은 **override가 아니라 correction**이다. "무엇을 고칠까"보다 **"무엇을 그대로 둘까"** 를 먼저 정해야
> 애니메이터가 만든 것이 살아남는다. 처음부터 축을 분해했다면 두 번의 왕복이 없었을 것이다.

## 9. 조용한 함정 세 가지

이번 트랙에서 나온, 서로 무관하지만 성격이 같은 것들 — **전부 에러 없이 잘못된 결과를 낸다.**

**① enum 중간 삽입이 SO를 밀어버린다.** `AnimationTriggerType`에 `Hit`을 알파벳 순서에 맞춰 중간에 넣었더니,
int로 직렬화돼 있던 기존 SO 값이 한 칸씩 밀려 **보스 슬램 큐가 다른 애니를 재생**했다. 테스트가 잡았다.
→ 규칙: **직렬화되는 enum은 항상 끝에 추가한다.** 보기 좋은 순서보다 값 안정성이 먼저다.

**② 에셋 캐시가 디스크보다 오래됐다.** 프리팹을 `DeleteAsset` 후 재생성했더니 YAML은 정확한데
런타임 컨트롤러가 null이었다. `Animator is not playing an AnimatorController` 경고가 **193건** 쏟아졌다.
→ `AssetDatabase.ImportAsset(ForceUpdate | ForceSynchronousImport)` 를 생성 직후 명시적으로 호출.

**③ 시간 기반 유일성은 유일하지 않다.** 전체 PlayMode에서 E2E 2건이 `NICKNAME_ALREADY_TAKEN`으로 실패했는데,
격리 재실행하면 **다른** 테스트가 같은 이유로 실패했다. 닉네임 생성기가 **밀리초 하위 6자리**만 쓰고 있었다 —
다중 클라 E2E는 두 계정을 같은 밀리초에 등록한다(게다가 6자리는 ~16.7분마다 순환해 이전 실행 DB와도 부딪힌다).
→ 시간 + 프로세스 일련번호 + 난수로 교체. 이후 202/202.

③은 기능 결함이 아니라 **검증 신뢰도** 문제라 더 중요하다. 실패가 무작위로 옮겨 다니면
"내 변경 때문인가"를 판단할 수 없고, 그 상태에서는 어떤 초록도 근거가 못 된다.

## 핵심 키워드

아바타 타입 = 계약(Generic ↔ Humanoid 리타깃) · 배선 완료 ≠ 재생됨(본 회전량 실측) ·
블렌드 좌표 = 클립 실측 속도(m/s)로 **단위를 바꿔 문제 소멸** · 보정 계수 대신 의미 교정 ·
제자리 클립의 배속 보정과 상한 초과분 속도 하향(한 원리 두 구현) · 오측정 > 미측정은 거짓 ·
타이밍 진실원을 애니메이터가 아닌 데이터로(서버 cadence와 자동 일치) · `hasExitTime` 트리거 소실 ·
선입력 버퍼의 의미는 단계마다 다르다 · 좌표계 명시(로컬/면 법선/캐릭터 기준) · 절반만 맞는 부호 버그 ·
**IK = override 아닌 correction**(무엇을 그대로 둘지 먼저 정하기) · 직렬화 enum은 끝에만 추가 ·
에셋 캐시 강제 재임포트 · 시간 기반 유일성의 충돌과 검증 신뢰도
