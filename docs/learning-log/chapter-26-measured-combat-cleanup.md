# 챕터 26 학습 로그 — AC 트랙: 측정이 이끈 전투 정리 (CombatTrace · Seq/송신큐 · 몬스터 레벨링)

> 이 트랙은 "체력 동기화가 느린 것 같다"는 **체감**에서 시작했다. 고치는 대신 먼저 **계측**을 만들었고, 그 데이터가 세 갈래로 이어졌다.
> ① 고치려던 것(틱레이트 조정)은 **"불필요" 판정** — 지연의 지배 요인은 RTT였다.
> ② 체감으로는 안 보이던 **진짜 결함 2건**(몬스터 HP 역행 D2 · 송신 비직렬화 D1)을 근본 수정했다.
> ③ "몬스터가 너무 물렁하다"의 진짜 원인이 **몬스터에 레벨이 없다**는 사실로 드러나, 밸런스 데이터 전체를 SO 파이프라인으로 재정비했다(던전 5개 L1→L30, 변종 = ID 직접 저작).
>
> 요약하면: **측정은 "무엇을 고칠지"만이 아니라 "무엇을 고치지 않을지"도 결정해 준다.**

---

## 1. 계측이 먼저다 — CombatTrace 3종 세트

"느린 것 같다"는 문장에는 고칠 수 있는 정보가 하나도 없다. 어디서(서버 판정? 브로드캐스트? 클라 적용?), 얼마나(10ms? 500ms?), 항상인지 가끔인지를 모르기 때문이다. 그래서 수정 전에 관측 경로부터 깔았다.

```
[서버]  CombatHandler / Room 틱
          → [CombatTrace] 구조적 로그 (Serilog Debug 스위치, 평시 비용 0)
             경로(P→M / M→P / P→P) · 산식 문자열 · 실제 스케일 입력 · 패킷 Seq
[클라]  소켓 수신 스레드
          → CombatTraceRecorder 링버퍼 4096 (struct, 무할당, Stopwatch 시계)
          → 몬스터별 동기화 집계는 링과 분리(회전해도 집계 안 잃음)
[에디터] CombatTraceWindow (타임라인 / 판정 / 몬스터 동기화 탭) → CSV 내보내기
```

측정 세션(C1c) 결과:

| 항목 | 측정값 | 해석 |
|------|--------|------|
| 공격 → HP 반영 지연 | **~37ms** | RTT 지배 — 서버 처리는 병목 아님 |
| stale 상태 드롭 | **0건** | 송신 FIFO(아래 §3) 후 역전 소멸 |
| 게이트 오거부 | **0건** | 쿨다운·cadence·마나 게이트 정상 |
| 데미지 산식 | 전 건 일치 | AP 25/16을 로그에서 역산해 대조 |

→ 검토하던 **C2b(틱레이트 상향)는 기각**. 37ms의 대부분이 왕복 지연이면 틱을 올려도 체감은 안 변하고 서버 비용만 는다. "고치지 않기로 한 결정"에 데이터 근거가 남았다는 것 자체가 이 트랙의 수확이다.

> 교훈: 성능/동기화 이슈에서 첫 커밋은 수정이 아니라 **계측**이어야 한다. 체감 기반 수정은 멀쩡한 것을 고치고(틱레이트), 진짜 결함(D1·D2)을 놓친다.

## 2. D2 몬스터 HP 역행 — Seq는 "언제" 찍는가가 본질

증상: 몬스터 HP가 줄었다가 **되돌아간다**. 원인은 상태 브로드캐스트의 순서 역전 — 늦게 만든(더 최신) 스냅샷이 먼저 도착한 패킷보다 늦게 적용되는 게 아니라, **오래된 스냅샷이 나중에 도착해 최신 값을 덮는** 것.

해법은 `S_MonsterState.Seq`(공개 계약 — 승인 후 변경). 그런데 구현하며 배운 핵심은 필드 추가가 아니라 **스탬프 시점**이었다:

```
send 시점 스탬프   →  "나중에 보낸 것 = 큰 번호"  → 역전된 송신 순서를 정당화해 버림 (틀림)
snapshot 시점 스탬프 → "나중에 만든 상태 = 큰 번호" → 클라가 seq <= applied 를 버리면 끝 (맞음)
```

시퀀스 번호의 의미는 "전송 순서"가 아니라 **"상태 생성 순서"**다. 몬스터별 `Interlocked.Increment`로 스냅샷 생성 순간 찍고, 클라는 적용된 번호 이하를 드롭한다. 이후 §3의 송신 FIFO가 역전 자체를 없애 실측 드롭 0이 됐고, Seq는 백스톱으로 남았다.

## 3. D1 송신 비직렬화 — 재현 안 됨 ≠ 버그 없음

여러 스레드(틱·핸들러)가 한 소켓에 동시에 `Send`하면 프레임이 절반씩 섞여 역직렬화가 깨질 수 있다. 수정은 세션당 **송신 큐 단일화**:

```csharp
Channel.CreateBounded<byte[]>(1024)   // SingleReader, 소비 루프 하나가 전체 프레임 단위로 write
TryWrite 만 사용                       // 틱 스레드는 절대 블록되지 않는다
큐 포화 → 그 세션 Disconnect            // 무한 큐 = 느린 클라가 서버 메모리를 먹는 DoS 벡터
```

흥미로운 건 검증 과정이다. "수정을 껐다 켜며 테스트가 실패를 잡는지" 확인하는 규율대로 우회 실험을 했는데 — **두 번 다 통과해 버렸다.** 첫 번째는 페이로드가 커널 버퍼보다 작아서, 두 번째는 **Windows의 overlapped WSASend가 전체 버퍼 완료까지 원자적**이어서다. 즉 이 버그는 Windows에선 구조적으로 재현이 안 되고, Linux(운영 환경)에선 실재한다.

> 교훈: "재현 안 됨"은 "버그 없음"이 아니라 "이 플랫폼에선 안 보임"일 수 있다. 그래서 이 수정의 근거는 재현이 아니라 **구조 보장**(송신 경로가 큐 하나로 수렴하므로 어떤 플랫폼에서도 프레임이 섞일 수 없다)이고, 테스트는 순서·포화·끊김 정책을 지킨다.
>
> 부수 효과: `SendPacketAsync`의 의미가 "전송 완료"에서 **"큐 적재 완료"**로 바뀌었다. API 시그니처가 같아도 의미가 바뀌면 계약 변경이다 — 주석으로 박제했다.

## 4. 관측 도구도 설계 대상이다 — "다른 플레이어가 한 건 기록이 안 되네"

클라 레코더 첫 판은 **내 스윙**만 기록했다(AttackSent에서 레코드 시작). 사용자가 바로 잡아냈다 — 검수 목적은 "내 데미지 확인"이 아니라 **던전 전체의 데미지·동기화 검수**인데, 다른 플레이어와 몬스터의 행동이 안 보이면 반쪽이다.

고치면서 드러난 설계 사실 두 가지:

1. **몬스터가 주는 데미지에는 `S_ApplyEffect`가 없다** — 클라 입장에서 몬스터 피해의 유일한 신호는 **HP delta**다. 그래서 레코더는 HP 변화 자체를 데미지 신호로 삼는다(이동 틱 delta 0은 제외).
2. 스윙의 출발점이 셋이라 조인 로직이 다르다 — `SwingOrigin{LocalPlayer, RemotePlayer, Monster}`. 송신→HP 지연은 로컬만 잴 수 있고, 발동→HP 지연은 셋 다 잴 수 있다.

그리고 이 결함을 단위 테스트가 못 잡았던 이유가 뼈아프다: 순수 로직 테스트는 내가 만든 입력으로 내가 만든 조인을 검증할 뿐, **실제 패킷 흐름에 그 입력이 존재하는지**는 묻지 않는다. 실배선 후에야 "주 시나리오(몬스터 데미지)에서 레코드 0건"이 드러났다.

> 교훈: 계측 코드도 기능 코드다 — 요구사항(누구의 무엇을 검수하는가)을 먼저 묻고, 실제 데이터 소스(어떤 패킷이 실재하는가)에 배선해 검증해야 한다.

## 5. 밸런스 붕괴의 진짜 원인 — 몬스터에 레벨이 없었다

C1c CSV가 보여준 것: L6 플레이어(DEF 15) 앞에서 몬스터 피해가 전부 **1**(산식 바닥값). 몬스터는 전원 저작 당시 스탯 그대로인데 플레이어만 성장하니, 밸런스는 시간이 지날수록 무너질 수밖에 없는 구조였다.

수정은 `MonsterLevelScaling` — 그런데 **상수를 하나도 넣지 않았다**:

```
base(L)  = net₁ · HP(L)/HP(1) + DEF(L)      // 몬스터 피해: 플레이어 HP 성장 비율을 따라간다
maxHp(L) = maxHp₁ · AP(L)/AP(1)             // 몬스터 체력: 플레이어 공격력 성장 비율을 따라간다
```

- 곱연산 배율(`dmg × k^L`)은 고데미지 스킬(슬램)이 폭발하고, 단순 가산(`dmg + L`)은 몬스터 간 역할 차이가 뭉개진다. **플레이어 성장 곡선(level-table)을 직독**하면 "L짜리 몬스터는 L짜리 플레이어에게 L1 때와 같은 체감"이 정의상 성립하고, 밸런스 조정 지점이 레벨 테이블 한 곳으로 수렴한다.
- **L1 = 항등**이라 레벨을 저작하지 않은 기존 데이터는 스탯이 1도 안 변한다 — 동작 보존 증분(테스트로 고정).
- 던전은 5개(L1·6·12·20·30), 대역·보상 단조 증가를 테스트가 강제한다.

## 6. AC-G — 배율 간접층을 버리고 "ID가 곧 변종"

엘리트/보스를 위해 처음 만든 것은 `MonsterScalingDefinition`(등급별 HP/피해 배율 테이블)이었다. 사용자가 기각했다 — *"Monster Table에 등급을 추가하고 ID로 구분하는 형태로. 그럼 ID만 처리하면 되잖아."*

바뀐 최종 형태:

```
배율 방식 (기각)                         ID 방식 (채택)
spawn: { id: leviathan, tier: Boss }    spawn: { id: leviathan_boss }
  → 런타임에 500 × 6.0 = 3000             → monsters.json 에 3000 직접 저작
  "왜 3000인지" 두 곳을 봐야 안다           한 곳(그 몬스터의 행)에 다 있다
```

- `tier`는 monsters.json의 **분류 필드로만** 남는다(보스 체력바·등장 연출용) — **절대 스탯에 곱하지 않는다**(테스트로 강제).
- 변종은 자기 드롭 테이블도 직접 갖는다 — 배율이 없으므로 테이블이 없으면 아무것도 안 떨군다(이것도 테스트).
- 이 전환 중 테스트가 내 저작 실수를 잡았다: leviathan base를 65로 착각하고 배율 환산해 보스를 390으로 적었는데, 원본이 500이라 "보스가 원본보다 물렁한" 모순 — `변종은_별개_ID_로_저작된다` 테스트가 즉시 실패했다.

> 교훈: 간접층(배율)은 코드를 줄여 보이지만 **데이터를 읽는 비용**을 늘린다. 기획 데이터는 "한 행을 보면 그 몬스터의 전부를 아는" 직접 저작이 낫고, 스폰·드롭·전투가 전부 `monsterId` 하나만 다루게 되어 코드도 오히려 줄었다.

## 7. 데이터 전부를 SO 파이프라인으로 — 그리고 에디터 자동화의 함정

이 트랙으로 게임 데이터 전체가 한 파이프라인으로 수렴했다:

```
Unity ScriptableObject 저작 (어빌리티 15 · 몬스터 13종 · 드롭 12 · 레벨 60 · 스폰 8맵)
  → Exporter bake → 서버 임베디드 JSON (Shared.Infrastructure/Resources)
  → 서버·클라가 같은 카탈로그를 읽음 (스킬·몬스터·던전 추가 = 서버 코드 수정 0)
```

지키느라 배운 것들:

- **Export만 있고 Import가 없으면** 부트스트랩(재생성)이 저작값을 지운다 — 모든 필드는 **왕복**이 완성 조건.
- Exporter 끝의 `EditorUtility.DisplayDialog`(모달)가 **MCP 자동화를 무기한 블록**했다 — Unity가 죽은 게 아니라 팝업이 입력을 기다린 것(사용자가 원인을 짚음). 자동화 경로는 팝업 없는 `BakeAll()`로 분리.
- 구운 JSON은 생성물이다 — 직접 수정 금지, 항상 SO를 고치고 다시 굽는다(생성물 수정은 다음 bake 가 조용히 되돌린다).

## 처음 생각한 것 → 피드백/데이터로 수정된 것

| 처음 생각 | 수정 | 계기 |
|-----------|------|------|
| 동기화가 느리니 틱레이트를 올리자 | 지연은 RTT 지배 — **조정 불필요** 판정 | C1c 실측 37ms |
| Seq는 보낼 때 찍으면 된다 | **스냅샷 생성 시점**에 찍어야 역전을 잡는다 | send 시점은 역전을 정당화함 |
| 송신 버그는 재현해서 증명하자 | Windows에선 구조적으로 재현 불가 — **구조 보장**으로 | 우회 실험 2회 통과 |
| 레코더는 내 스윙만 기록하면 된다 | 검수 목적 = **전 액터·전 몬스터** | 사용자: "다른 플레이어가 한 건 기록이 안 되네" |
| 등급 = 배율 테이블 | **변종 = 별개 ID 직접 저작**, 등급은 분류만 | 사용자: "ID만 처리하면 되잖아" |
| 스케일 상수는 튜닝하며 정하자 | **상수 0** — 플레이어 성장 곡선 직독 | 조정 지점이 두 곳이면 반드시 어긋남 |

## 핵심 키워드

- **측정 우선(observability-first)** — 수정 전에 계측. 데이터는 "고칠 것"과 "고치지 않을 것"을 모두 결정한다.
- **시퀀스 스탬프 시점** — 번호의 의미는 전송 순서가 아니라 상태 생성 순서. send-time 스탬프는 역전을 정당화한다.
- **bounded send queue** — TryWrite(생산자 무블록) + 포화 시 끊기(무한 큐 = DoS). "재현 안 됨 ≠ 버그 없음", 구조 보장으로 증명.
- **HP delta = 몬스터 데미지의 유일 신호** — 계측은 실재하는 패킷에 배선해 검증해야 한다(순수 로직 테스트의 한계).
- **상수 0 스케일** — `MonsterLevelScaling`은 level-table 비율만 읽는다. L1 항등 = 동작 보존 증분.
- **변종 = ID** — 배율 간접층 제거, 등급(tier)은 분류 전용. 한 행 = 그 몬스터의 전부.
- **SO 저작 → bake** — Import 왕복 필수, 자동화는 모달 없는 경로로, 생성물 직접 수정 금지.
