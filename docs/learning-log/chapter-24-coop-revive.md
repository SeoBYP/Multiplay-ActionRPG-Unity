# 챕터 24 학습 로그 — Co-op 부활: 서버 권위 재사용 · 결정 뒤집기 · DI vs 컴포넌트

> 다운된 아군을 살리는 협력 메커닉. "이 포트폴리오가 약속한 Co-op"의 마지막 조각.
> 구현 자체보다 **세 가지 교훈**이 남았다.
> ① 한 기능의 요구가 **과거의 설계 결정을 뒤집을 수 있다**(원격 다운 = Destroy → 보존).
> ② "아예 안 되던" 진짜 원인은 로직이 아니라 **의존성을 잘못된 방법으로 가져온 것**(DI vs 컴포넌트).
> ③ 그 DI 회귀를 잡은 건 **전체 PlayMode 스위트**였다 — 단위·컴파일은 통과했었다.

---

## 1. 서버 권위 골격을 또 재사용 — 새 패킷 2개로 끝

부활도 새로운 게 거의 없었다. HP(챕터 21)·마나(챕터 23)·회피에서 쓴 **"클라 입력 → 서버 권위 검증 → 브로드캐스트"** 골격을 그대로 얹었다.

```
아군 다운(State.Dead/HP0) — 기존(2.5.1)
   → 시전자 사거리 안 + E → C_Revive{TargetUserId}
   → 서버 Room.TryRevive 검증: ①자기제외 ②미실패 ③시전자 생존 ④대상 다운 ⑤거리
       → HP=MaxHp×50% + _downed.Remove(멱등)
   → S_PlayerRevived{UserId, Hp} 방 브로드캐스트
```

검증 항목을 한 메서드(`Room.TryRevive`)에 모아 **멱등**으로 만든 게 핵심. 중복 C_Revive가 와도 `_downed.Remove`가 false면 그냥 거부 — 두 번 살아나거나 두 번 HP가 차는 일이 없다. "검증·상태변경을 한 곳에 원자적으로"는 회피(`TryBeginDodge`)에서 배운 패턴의 반복이다.

> 권위 경계: 홀드 시간 같은 UX는 클라가, **거리·다운상태처럼 게임 결과를 바꾸는 불변식은 서버가**. 부활은 데미지 익스플로잇이 아니라 저위험이라 거리/상태만 서버가 보면 충분하다.

## 2. 한 기능이 과거 결정을 뒤집다 — "Destroy → 보존"

2.5.1에서 **원격 플레이어가 다운되면 그 캐릭터를 Destroy**했다(다운을 남에게 보이게 하는 게 목적이었고, 다운 포즈는 후속이라 그냥 지웠다). 그런데 부활을 붙이려니 이 결정이 정면으로 막았다 — **살리려면 다운된 아군이 상호작용 대상으로 살아 있어야 한다.** 지워버리면 다가가도 아무것도 없다.

그래서 `CharacterSpawner.HandlePlayerDead`의 원격 분기를 **Destroy → 다운 보존(DownedAllyMarker 부착)**으로 뒤집었다.

```
2.5.1: S_PlayerDead{원격} → DespawnRemote(Destroy)        ← 부활 불가
2.5.2: S_PlayerDead{원격} → DownedAllyMarker 부착(보존)   → 부활 대상
       S_PlayerRevived{원격} → 마커 제거(정상 복귀)
```

교훈: **"지금 안 쓰니까 간단히 지운다"는 결정은, 나중 기능이 그 흔적을 필요로 할 때 빚이 된다.** 다만 그때 미리 만들지 않은 건 옳았다(YAGNI) — 필요해진 시점에 한 줄로 뒤집었으니. 핵심은 *되돌릴 수 있게* 국소화해 둔 것.

## 3. "아예 안 되던" 진짜 원인 — DI vs 컴포넌트

코드·단위·E2E가 다 그린인데, MPPM으로 켜보니 **부활이 전혀 동작하지 않았다. 로그조차 한 줄도 안 떴다.**

처음엔 마커 탐지나 입력 폴링을 의심했다. 진짜 원인은 한 줄이었다:

```csharp
// CharacterSpawner — 내가 쓴 코드
var input = _container.TryResolve(typeof(ICharacterInputSource), out var i) ? ... : null; // 항상 null!
```

`ICharacterInputSource`를 **DI 컨테이너에서** 가져오려 했는데, 이 프로젝트에서 입력은 **DI 등록이 아니라 플레이어 GameObject에 붙은 컴포넌트**(`CharacterInputBuffer`)다. 에이전트도 이렇게 가져온다:

```csharp
// CharacterAgent.cs — 원래 있던 방식
InputSource = GetComponent<ICharacterInputSource>();
```

내 `TryResolve`는 항상 null을 돌려줬고, `ReviveInteractor.Update`는 첫 줄 `if (_input == null) return;`에서 매 프레임 빠져나갔다 — 그래서 **로그조차 안 떴다.** 고친 건 한 줄: `GetComponent<ICharacterInputSource>()`로 바꾸니 즉시 동작했다.

> 교훈: 의존성을 *소비*하기 전에 그게 **어떻게 제공되는지**(DI 등록 vs 씬 컴포넌트 vs 수동 주입)를 알아야 한다. 가장 안전한 길은 **이미 같은 걸 쓰는 소비자를 그대로 따라하는 것** — 에이전트가 `GetComponent`로 가져오면 나도 `GetComponent`다. "있겠지" 하고 DI에서 찾은 게 화근이었다.

(겸사겸사 사용자 요청으로 홀드 채널을 걷어내고 **사거리+E 즉시**로 단순화했다. 코어가 먼저 동작해야 UX를 얹는다 — 홀드는 그다음 폴리시.)

---

## 4. 그 회귀를 잡은 건 "전체 스위트"였다

입력 버그와 별개로, 코드를 처음 짰을 때 **단위·컴파일은 다 통과**했다. 그런데 사용자가 "실 테스트 전에 E2E·PlayMode를 *전부* 통과시켜라"고 못 박아서 **전체 PlayMode**를 돌렸더니 2건이 빨갛게 떴다:

```
CharacterSpawnMultiClientTests
VContainerException: No such registration of type: ICharacterInputSource
```

처음엔 `ReviveInteractor`를 `[Inject]`로 만들었는데, **스폰 전용 테스트 스코프엔 입력이 등록돼 있지 않아** `_container.Inject`가 throw했다. 부활과 무관한 *스폰 테스트*가 깨진 것 — 단위/컴파일/부활 E2E만으론 절대 못 봤다. (이후 `GetComponent` 전환으로 DI 의존 자체가 사라져 근본 해소.)

> 교훈(사용자 지적, 박제): **"플레이 검증은 사용자 영역"으로 넘기기 전에, E2E + PlayMode 전체를 내가 먼저 그린으로 만든다.** 단위만 보면 인접 기능의 회귀가 조용히 샌다. 느린 liveness 테스트(72s·80s)가 있어도 전체를 돌린다 — 사람이 켜서 깨진 걸 발견하는 것보다 싸다.

---

## 처음 생각한 것 → 피드백으로 수정된 것

- **"입력은 DI에 있겠지"** → 아니다. 씬 **컴포넌트**(`CharacterInputBuffer`)다. `TryResolve`는 항상 null → 로그조차 0. 같은 걸 쓰는 `CharacterAgent`(GetComponent)를 따랐어야 했다.
- **"단위+컴파일 그린이면 됐지, 플레이는 사용자가"** → 아니다. **전체 PlayMode**가 인접 스폰 테스트의 DI 회귀를 잡았다. 실 테스트 전 자동 검증 전체가 먼저.
- **"홀드 채널부터 정교하게"** → 코어(범위+E)가 먼저 동작해야 한다. UX 폴리시는 그다음.
- **"원격 다운은 지우면 되지(2.5.1)"** → 부활이 그 결정을 뒤집었다. 간단히 지운 것이 나중 기능엔 빚 — 단, 국소화해 둬서 한 줄로 되돌림.

## 핵심 키워드

- **서버 권위 골격 재사용**: 클라 입력 → 서버 검증(불변식) → 브로드캐스트. HP/마나/회피/부활이 같은 틀.
- **원자적 멱등 검증**: 검증+상태변경을 한 메서드에. 중복 요청은 `Remove`가 false면 거부 → 두 번 안 산다.
- **결정 뒤집기 비용**: "지금 간단히"가 나중 기능엔 빚. 단, 국소화하면 되돌리기는 한 줄.
- **DI vs 컴포넌트 vs 수동주입**: 의존성을 소비 전 *제공 방식*을 확인. 가장 안전 = 기존 소비자 모방.
- **전체 스위트의 가치**: 단위·컴파일은 인접 회귀를 못 본다. 실 테스트 전 E2E+PlayMode 전체 그린.
